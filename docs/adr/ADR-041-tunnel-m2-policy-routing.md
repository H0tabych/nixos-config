# ADR-41: режим M2 — нативный TUN и политика маршрутизации по метке; вердикт гейта 7.3 от 2026-10-14 отозван

- Статус: принято; реализация и проверка в ВМ — ROADMAP.md R5.4; на машине подтверждается гейтом 7.3
- Источник: разбор вердикта 2026-10-14 и контрольные прогоны в ВМ 2026-11-05; ROADMAP.md D10, D12, D13; VPN_SUBSYSTEM.md 4.1, 4.4, 4.5, 7.3
- Решение: виртуальный интерфейс создаёт нативный TUN-inbound ядра туннеля, адрес и маршруты задаёт ОС. Собственный трафик клиента исключён из туннеля меткой сокета и политикой маршрутизации по схеме wg-quick:
  ```
  32000: lookup main suppress_prefixlength 0
  32001: not fwmark <метка> lookup 7777
  table 7777: default dev <интерфейс> metric 1; unreachable default (низший приоритет)
  ```
  Правила и `unreachable` ставятся до подъёма сети и не зависят от клиента. Метка клиента сохраняется в отслеживании соединений и восстанавливается на входе, поэтому проверка обратного пути файрвола остаётся строгой. Файрвол — на nftables в обоих режимах. Пакет ядра туннеля — из нестабильного канала (VPN-CLI-11). R9.6 выполняется до включения M2.
- Причина: M2 блокировала не версия ядра туннеля, а дефекты нашей конфигурации. Прежняя причина, отсутствие IPv4 на устройстве, опровергнута прогоном.
- Затронутые правила: NET-7, NET-8; VPN-MOD-12 (новое); VPN-KS-2, VPN-KS-6, VPN-KS-11 (новое); VPN-DNS-2, VPN-DNS-9 (новое); VPN-CLI-11; VPN-RTE-3; AI_SUBSYSTEM 8.4; ROADMAP R5.4, R5.5, R9.6, G8

## Разбор вердикта 2026-10-14

Тогда две попытки включить M2 на единственной машине закончились потерей сети. Причиной записали «tun-инбаунд не назначает устройству IPv4-адрес, ядру неоткуда взять адрес источника». Это не проверялось отдельно: различить причины на рабочей сети было нечем.

В `tests/tunnel-m2.nix` сеть полностью внутренняя, поэтому каждую причину можно вернуть по одной. Все прогоны — на исправленной конфигурации с одним возвращённым дефектом:

| Что возвращено | Результат прогона | Вывод |
|---|---|---|
| Нет upstream у резолвера (`DNS=` пуст, `networkmanager.dns = none`) | По адресу через туннель: адрес выхода. По имени: `curl` код 6, `getent` код 2 | Любое обращение по имени падает. Этого одного хватало для «сеть пропала» |
| Прежний kill switch: `oifname "tun*"` при имени устройства `xray-tun0` | Маршрут через устройство есть, `curl` по адресу — код 7, отказ | Весь трафик приложений отвергался собственным kill switch'ем |
| Метка не восстанавливается на входе | `curl` — код 28. В журнале ядра `rpfilter drop: IN=eth1 SRC=<выход> SPT=443 ACK SYN` | Файрвол отбрасывал ответ выхода: обратный путь проверялся по таблице туннеля. Удаление таблицы kill switch этого не лечит, что и наблюдалось 2026-10-14 |
| Нет метки на исходящем `direct` (D10) | `curl` до адреса локальной юрисдикции — код 28, записей conntrack с 20 до 3974 за 8 с | Петля |
| Нет правила `suppress_prefixlength` (как в прежней схеме) | `10.0.0.1` и `172.17.0.2` уходят в `dev tunnel0` вместо `eth1` и `docker0` | В туннель уходили LAN, мосты контейнеров и корпоративный VPN |
| **Заявленная причина: нет IPv4 на устройстве** | Адрес снят, маршрут через устройство оставлен: `curl` по адресу и по имени вернули адрес выхода. И на 26.10.31, и на 26.3.27 | **Опровергнута.** Ядро берёт адрес источника с другого интерфейса |

Вердикт отозван. Адрес на устройстве всё равно ставится: так соединения приложений не зависят от адреса физического интерфейса, а для DNS есть постоянная точка входа.

## Что ещё исправлено

- `ct state established` стоял первым правилом kill switch: при остановке клиента открытые соединения уходили бы на физический интерфейс мимо туннеля (VPN-KS-11).
- Цепочка `forward` расходилась с P.5: новые соединения между контейнерами получали бы отказ.
- Sniffing без `routeOnly` заменял цель соединения доменом, и при стратегии `AsIs` правила по IP не срабатывали (VPN-RTE-3).
- Резолвер отправлял в туннель запросы LLMNR и mDNS, а клиент выпускал их напрямую: на интерфейсе туннеля выключен multicast.
- DNS-модуль Xray работает только с A и AAAA, на остальные типы уходил пустой ответ: теперь они идут через туннель по DoT (VPN-DNS-9).
- Включение M2 молча переводило файрвол с iptables на nftables. Теперь бэкенд один в обоих режимах, переключение режима файрвол не меняет. Docker работает через iptables-nft и совместим с этим: `flushRuleset` остаётся выключенным, его таблицы не стираются.

## Что подтверждено в ВМ

Сквозной тест на настоящих фичах клиента и настоящем рукопожатии Reality, с захватом пакетов на стороне провайдера: VPN-A5, VPN-A6, VPN-A7 (без браузера), VPN-A8 (остановка, падение, холодный старт), VPN-KS-6, VPN-MOD-5 (откат на M1 и обратно), M2-1 (без QUIC), M2-2, M2-3 (смена шлюза), M2-5, M2-6, M2-8 (без `bypass.units`).

Только на машине остаются: M2-3 с настоящим Wi-Fi, M2-4, M2-7, M2-10, M2-1 для QUIC, VPN-A7 с браузером, VPN-A9, VPN-A10, корпоративный VPN поверх туннеля (VPN-INT-5, D6) и работа с NetworkManager: в ВМ сеть настроена статически.

## Версия ядра туннеля

Прогоны в ВМ, выход одной и той же версии:

| | 26.3.27 (26.05) | 26.10.31 (`nixos-unstable`) |
|---|---|---|
| Один поток через туннель | 8 МБ/с | 42 МБ/с |
| CPU клиента на гигабайт | 57 с | 8 с |
| UDP к произвольному порту (M2-1) | Отказ соединения, на обеих версиях выхода | Работает |
| Типы записей кроме A и AAAA (VPN-DNS-9) | Пустой ответ: поля `rules` у исходящего `dns` нет | Работает |
| Остальной сценарий `tests/tunnel-m2.nix` | Проходит | Проходит |

Причину отказа UDP на 26.3.27 не разбирал: запрос DNS через ту же версию проходит.

Оба смешанных сочетания работают при отпечатке `chrome`: клиент 26.10.31 с выходом 26.3.27 проходит весь сценарий, клиент 26.3.27 с выходом 26.10.31 — весь, кроме двух строк таблицы. Поэтому порядок обновления клиента и выхода не важен. Reality 26.9.8+ отвергает ClientHello без X25519MLKEM768, так что при другом отпечатке совместимость надо проверить отдельно.

Выбрана 26.10.31 (VPN-CLI-11): 26.3.27 не выдерживает M2-1, значит условие M2-9 для стабильного релиза не выполнено. TCP-стеку новой версии всего несколько недель, это отслеживается наблюдением R9.10. Откат на 26.3.27 — один атрибут `pkg` в `tunnel-xray.nix`, но с потерей UDP и типов записей из таблицы выше, а проверку M2 в `tests/tunnel-config.nix` придётся перенести в ВМ.

## Отклонённые варианты

1. **Автомаршрутизация Xray (`autoSystemRoutingTable`, `autoOutboundsInterface`).** Маршрут ставится в `main`, поэтому строгий rpfilter пришлось бы ослаблять на весь хост. Автоопределение интерфейса уже ломалось (L-16, Xray-core#6412), а связанная привязка `sockopt.interface` может молча не сработать (Xray-core#7160, открыт).
2. **`gateway` в конфиге Xray.** Рабочий вариант, но без него конфиг не зависит от версии, а адрес и маршрут всё равно задаются вместе.
3. **`autoSystemDnsToGateway`.** Xray вызывал бы `resolvectl` сам, а владелец резолвера — `dns-resolver` (ADR-34).
4. **Ослабить rpfilter (`checkReversePath = "loose"`).** Одна строка, но при маршруте по умолчанию в туннель проверка теряет смысл для всего хоста. Восстановление метки сохраняет её строгой.
5. **Посредник «tun → SOCKS» (tun2socks).** Лишний компонент и звено: нативный TUN справляется сам.
6. **sing-box, dae.** Штатный sing-box без проверки ML-DSA-65 (VPN-CLI-3) и не подключается к Reality на Xray 26.9.8+ (sing-box#4520). У dae поддержку не проверял: его правила работают на eBPF, а не на виртуальном интерфейсе (VPN-MOD-3).
7. **nftables TPROXY.** Рабочий, но больше правил, и нет интерфейса, на котором стоит контракт VPN-MOD-3. Запасной вариант, если TUN не пройдёт гейт на машине.
8. **WireGuard до выхода.** Без маскировки, против VPN-SRV-3.
9. **Разделить G8 и отложить M2.** Предлагалось до этого разбора. Блокирующей внешней причины больше нет.

## Порядок работ

- **R8.5 и гейт 7.3.** ROADMAP и AI_SUBSYSTEM 8.4 требовали для облачных ролей M2, а R8.5 был отмечен выполненным в M1. Роли работают и в M1; от гейта зависят только части AI-A5 и AI-A9 про M2.
- **R9.6 вперёд.** G8 через AI-A5 и AI-A9 зависит от гейта 7.3, гейт через M2-10 от маршрута `direct`, а этап 9 открывался только после G8. Кроме того, без `direct` отказ выхода в M2 повторил бы инцидент 2026-11-04 (ADR-40). R9.6 выполняется до включения M2.

## Что не меняется

- Режимы и их переключение (NET-7, VPN-MOD-5), маршрут `direct` (ADR-40), секреты (SEC-4), политика (VPN-RTE-1…8).
- На машине режим остаётся M1 до гейта 7.3.
- Исключение ADR-39 снимается вместе с переходом на M2, по его условию.

## Условие пересмотра

- Гейт 7.3 не пройден на машине по причине, которую нельзя устранить в этой схеме: тогда сначала TPROXY, затем разделение G8 по образцу ADR-35 с уже точной причиной.
- Появится `tunneled` для IPv6 (VPN-DNS-4): политику маршрутизации надо повторить для IPv6, сейчас она только для IPv4.

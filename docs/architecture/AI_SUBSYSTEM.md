# Подсистема ML и агентов — подключаемая часть системы

> Версия 2.1 · 2026-10-08 · Статус: действующий (изменения 2.1 — Приложение R)
> **Подчинена** нормативному документу «Архитектура NixOS-систем» (далее — **Архитектура**, v2.0). Не дублирует его: на правила Архитектуры даются ссылки по ID. При любом расхождении приоритет у Архитектуры.
> **Части 0–10** описывают подсистему без имён конкретных программ и версий (ARCH-16, ARCH-18). **Приложение P** — профиль реализации (информативно, меняется без ADR). **Приложение T** — что отменено относительно прежней v1.1 и почему. **Приложение C** — матрица соответствия Архитектуре.
> Документ не содержит секретов и приватных фактов (SEC-5); в примерах — плейсхолдеры `<…>`.

## 0. Подчинение и соглашения

**0.1 Что это.** Подсистема — это набор фич домена `ai` (раздел 6 Архитектуры) и capability `ml` (USER-4). Она подключается композицией: nixos-пресет `ml` для хоста и homeManager-пресет `ml` для пользователя (FEAT-5). Ни `enable`-опций, ни собственных точек входа у неё нет (ARCH-6).

**0.2 Что не дублируется.** Каркас и структура репозитория (разделы 3–4), контракт фичи (5.1), реестр пользователей (5.2), dotfiles-слой (8), секреты (9), хранилище и гибернация (10), сеть и туннель (11), рабочий стол (12), разработка (13), игры (14). Здесь описано только то, что специфично для ML и агентов, и то, как оно стыкуется с перечисленным.

**0.3 Условие непротиворечивости.**
- Документ **не изменяет** разделы 2, 3, 8–11 Архитектуры; ADR по OPS-7 для этого не требуется.
- Дополнения к каталогу (раздел 6) и реестру `my.*` (5.3) вносятся **в том же изменении**, что и фичи (FEAT-7). Перечень — в разделе 9.
- Реестр ADR расширяется записями ADR-20…24 (раздел 9), сформулированными без названий программ.

**0.4 Соглашения.** MUST / MUST NOT / SHOULD / MAY — по RFC 2119. ID правил подсистемы: `AI-<область>-<n>` (`INF`, `CMP`, `GW`, `AGT`, `CTX`, `RES`, `SEC`, `OPS`, `ROLE`). `ПРОВЕРИТЬ` — как в п. 0.1.5 Архитектуры: не подтверждено, дана проверка. Идентификаторы и пути — английские; текст — русский.

**0.5 Расположение.** Файл лежит рядом с Архитектурой; ссылка на него — из `docs/README.md`. Эксплуатационные заметки подсистемы — в `docs/runbook.md` (OPS-8), решения — в `docs/adr/`. Отдельных каталогов документации подсистема не заводит.

## 1. Роль и границы

### 1.1 Что входит

| Область | Содержание |
|---|---|
| Локальный инференс | Системный сервис на хосте (ML-3), модели по политике VRAM |
| Доступ к моделям | Пользовательский шлюз: стабильные имена ролей поверх локальных и облачных моделей |
| Ассистенты для разработки | Автодополнение (FIM) и чат в редакторах; клиентская часть живёт в dotfiles редактора |
| Агентные CLI | Контролируемый, альтернативный автономный и тяжёлый автономный; запуск только через изолирующий лаунчер |
| Контекст кода | Поиск по тексту и структуре, символьные запросы поверх LSP, MCP-серверы |
| Дисциплина ресурсов | Совместное использование дискретной GPU с играми, сном и гибернацией |

### 1.2 Что не входит (и у кого)

| Не входит | Владелец |
|---|---|
| Драйвер GPU, гибридная графика, питание GPU | `hardware/gpu-*` (DESK-5) |
| Бинарный кэш вычислительной платформы | существующая фича `compute-cache` (ML-2); здесь только ограничения использования (3.7) |
| GPU в контейнерах | `container-gpu` (ML-4) |
| ML-библиотеки, обучение моделей, ноутбуки | проектные окружения и шаблон `ml-cuda` (ARCH-9, ML-6, A.5) |
| Туннель, DNS, kill switch | `network/*` (раздел 11); подсистема лишь потребитель (ML-7) |
| Пакет редактора, LSP, менеджер плагинов | `dev/editor-<р>`, `lsp-global` (DEV-1, DEV-4) |
| Веб-интерфейсы LLM-сервисов, блокирующих адреса дата-центров | backlog сети (NET-12) |
| Игровая платформа и оптимизатор | `gaming/*` (APP-4); стык — п. 5.3 |

### 1.3 Задачи и языки

Автодополнение; чат по файлу и фрагменту; объяснение чужого кода; поиск ошибок; рефакторинг; тесты; анализ репозитория и поиск использований символов; агентные задачи с обязательным ревью человеком.
Языки — по профилю Архитектуры (A.5): Python, C/C++, Rust, SQL; вспомогательно Nix, Lua, Bash. Объём проектов — до ~1000 файлов.

### 1.4 Явные не-цели

1. Полная замена разработчика; применение опасных изменений без подтверждения.
2. Локальные модели, не помещающиеся в ресурсы хоста, без явного предупреждения.
3. **Второй локальный инференс-сервер на хосте** и отдельный сервер автодополнения (ADR-20).
4. **Собственная разработка** индексатора, векторного поиска, роутера моделей и песочницы, пока не пройден гейт 8.3.
5. Отправка приватного кода в облако без явного разрешения проекта (AI-SEC-9).

## 2. Точки подключения к Архитектуре

### 2.1 Capability и пресеты

- Capability: **`ml`** (уже есть в словаре, USER-4). Новых слов не вводится.
- nixos-пресет `ml` (`modules/presets/ml.nix`), помимо существующих фич домена (`compute-cache`, `container-gpu` — по составу Архитектуры), включает: `ai-facts`, `inference-service-<р>`, `llm-gateway`.
- homeManager-пресет `ml`: `llm-gateway`, `agents-tools`, `code-context`.
- Хост подключает системную часть пресетом `ml` в композиции (HOST-1). Пользователь получает пользовательскую часть автоматически по capability (USER-3).

### 2.2 Дополнения к каталогу (раздел 6, домен `ai`)

| Фича | Путь | Класс | Для кого | Назначение (владеет) |
|---|---|---|---|---|
| `ai-facts` | `modules/ai/ai-facts.nix` | N | хост | Объявление nixos-опций `my.ai.*` (аналог `host-facts`) |
| `inference-service-<р>` | `modules/ai/inference-service-<р>.nix` | N | хост | Инференс-сервис: пакет, юнит, политика моделей, команда `inference-release` |
| `llm-gateway` | `modules/ai/llm-gateway.nix` | N+H | пользователи с `ml` | N: объявление пользовательских секретов; H: юнит шлюза и его конфиг |
| `agents-tools` | `modules/ai/agents-tools.nix` | H | пользователи с `ml` | Пакеты агентных CLI и **лаунчер-песочница** (единственный способ запуска) |
| `code-context` | `modules/ai/code-context.nix` | H | пользователи с `ml` | Пакеты MCP-серверов и инструментов структурного поиска |

Уже существующие фичи домена (`compute-cache`, `container-gpu`, а также реализации слотов `dev/*`) не изменяются. Фичи `inference-service` и `agents-tools` уже есть в каталоге Архитектуры (раздел 6, v2.1): здесь они **уточняются** (слот `inference-service-<р>`, контракты 3.1 и 3.4), а не добавляются.
Одна фича — один владелец (ARCH-1); каждая включена в пресет (FEAT-8); каждый файл ≲ 150 строк (ARCH-12).

### 2.3 Дополнения к реестру `my.*` (раздел 5.3)

Все значения публичны (класс C) и не секретны; объявляются: внешний уровень — в `modules/core/options.nix`, nixos-уровень — фичей `ai-facts` / `host-facts`.

| Опция | Уровень | Назначение |
|---|---|---|
| `my.host.gpu.compute` | nixos (`host-facts`) | Вычислительный бэкенд хоста: `cuda` / `vulkan` / `none`. Факт железа: нужен, чтобы общие фичи не содержали вендор-специфики (ARCH-10, HOST-3) |
| `my.host.gpu.computeCapability` | nixos (`host-facts`) | Версия вычислительных возможностей GPU (для NVIDIA — `7.5`): целевые архитектуры сборки вычислительных пакетов и проверка ML-1; факт железа |
| `my.ai.inference.{host,port}` | nixos | Loopback-адрес инференса (читают шлюз, машинный слой) |
| `my.ai.inference.keepAlive` | nixos | Время жизни загруженной модели в простое (AI-RES-2) |
| `my.ai.inference.modelsDir` | nixos | Каталог моделей; читает `backup` для исключения (STO-8) |
| `my.ai.local.<роль>` | nixos | **Вычисляемо**: роль → локальная модель. Заполняет фича инференса, читает шлюз (не вводится вручную) |
| `my.ai.gateway.portBase` | nixos | Базовый порт пользовательских шлюзов; порт шлюза пользователя = `portBase` + (uid − 1000) (AI-GW-1) |

Значения никогда не передаются через `specialArgs` (ARCH-8): HM-часть читает их как `osConfig.my.*`.

### 2.4 Dotfiles-слой (раздел 8)

**Граница владения (DOT-3).** Nix даёт: пакеты, юнит шлюза, лаунчер, секреты, значения машинного слоя. Содержимое конфигов агентных CLI и клиентов редакторов — **dotfiles**. Nix эти конфиги не генерирует.

Предлагаемые записи реестра (`REGISTRY.md`; каждая — с ADR-lite по DOT-2 и версионной заметкой по DOT-10, т. к. ПО быстро меняется — L-14):

| Запись | Содержание | Примечание |
|---|---|---|
| Агентный CLI × 3 (по роли) | Права, песочница приложения, список MCP, ссылки на роли моделей | Расположение конфига вне `~/.config` — через переменную окружения от системы (DOT-12); ПРОВЕРИТЬ по каждому приложению |
| Каталог редактора (существующий) | Клиент автодополнения/чата как плагин; lock плагинов — в dotfiles (DOT-11) | Не новая запись |
| `ai/` (общий источник, по образцу `theme/`) | Единый список MCP-серверов + генератор форматов агентов (результат коммитится); необязательный диагностический скрипт | Единый источник — ARCH-5; по образцу DOT-9 |

**Машинный слой (DOT-5, DOT-6).** Каталог `~/.config/machine.d` создаёт и
владеет им `dotfiles-link`; отдельные файлы в нём пишут сами фичи-потребители
напрямую своим `systemd.tmpfiles.rules` — по прецеденту `zsh-env`
(`shell-zsh.nix`), а не через передачу значений владельцу каталога:

| Значение | Файл | Источник | Потребитель |
|---|---|---|---|
| Адрес инференса, роль→модель (`local-fast`/`local-chat`) | `ai-env` (R8.4, `inference-service-ollama`) | `my.ai.inference`, `my.ai.local` | Клиенты редакторов, агенты |
| Адрес пользовательского шлюза | — (R8.5) | `my.ai.gateway.portBase` + (uid − 1000) | Агенты |

Конфиги пишутся по DOT-13: «значение окружения, иначе умолчание». Констант хоста и путей `/nix/store` в dotfiles нет (DOT-1); имён конкретных моделей в dotfiles нет (AI-ROLE-2) — только переменная, значение которой подставляет Nix.

### 2.5 Секреты (раздел 9)

| Секрет | Класс | Файл | Потребитель | Доставка |
|---|---|---|---|---|
| Ключи API провайдеров (по одному на провайдера) | A | `secrets/users/<имя>.yaml` | Шлюз пользователя | sops → шаблон конфига, 0400, credentials (SEC-4) |
| Ключ доступа к шлюзу | A | `secrets/users/<имя>.yaml` | Шлюз и лаунчер того же пользователя | sops, 0400; лаунчер кладёт его **только** в окружение агента |
| Токены, которые приложение само сохраняет при входе | D | домашний каталог, вне репозиториев | Само приложение | Лаунчер открывает приложению только его каталог |

Секретов уровня хоста у подсистемы нет: локальные модели ключей не требуют. Имена ключей в YAML нейтральные (SEC-3). Ключи пользователя изолированы от других пользователей (USER-7, A17).
Секреты — не в `home.sessionVariables`, не в конфигах оболочки, не в dotfiles (ML-5).

### 2.6 Сеть (раздел 11)

- Подсистема **не определяет** маршрутизацию и переменные прокси. Облачные запросы идут через туннель в режиме M2 без настройки приложений (ML-7, NET-7).
- В запасном режиме M1 переменные прокси задаются только в одном месте (NET-10); AI-фичи их не дублируют (L-7).
- Все слушатели подсистемы — только loopback (NET-4); порты в firewall не открываются (NET-11).
- Готовность облачных ролей зависит от критериев A6. Остановка туннеля блокирует внешний трафик (NET-8) — это штатное состояние, а не сбой подсистемы; отсюда fallback (AI-GW-5).
- Загрузка моделей — разовая сетевая операция; в M2 покрывается автоматически, в M1 демоны переменных не читают (NET-7) — в этом случае загрузка выполняется вручную из сессии пользователя.

### 2.7 Требования к смежным доменам

| Домен | Что требуется | Форма |
|---|---|---|
| `hardware/gpu-*`, `power` | Дискретная GPU засыпает в простое и после выгрузки модели (A5, DESK-5); работает после resume (A13) | Критерии AI-A3, AI-A5; настройки питания — у владельца железа |
| `gaming/game-optimizer-<р>` | SHOULD вызывать `inference-release` при старте игры, если команда есть в PATH | Предложение владельцу слота; единственный владелец хука игры — оптимизатор (FEAT-6) |
| `storage/backup` | MUST исключать `my.ai.inference.modelsDir` (STO-8, ML-3) | Чтение опции; без дублирования пути |
| `storage/layout` | Том для данных сервисов вне снимков (Архитектура STO-1, v2.1): под `my.ai.inference.modelsDir` | AI-INF-8 |
| `storage/ephemeral-root` | Если включён (STO-7): каталог моделей и состояние сервиса — в едином persist-списке | Условно |
| `dev/*`, `shell/env-manager` | Агенты и MCP-серверы запускаются в проектном окружении (ARCH-9, DEV-4) | AI-SBX-4 |
| `dev` шаблоны (DEV-3) | MAY содержать заготовку инструкций для агентов | Необязательное расширение шаблонов |
| `security/sops` | Доставка пользовательских секретов | Через механизм фичи `sops`; ПРОВЕРИТЬ (NixOS- или HM-модуль) |
| `security/hardening` | MUST NOT отключать непривилегированные пользовательские пространства имён (иначе лаунчер не стартует, а fail-closed AI-SBX-6 сделает агентов неработоспособными); либо иной механизм изоляции — решением ADR | AI-SBX-11 |
| `base/nix-settings` | Политика unfree-пакетов определяется один раз (ARCH-5); пакеты подсистемы должны быть в ней допущены | ПРОВЕРИТЬ |
| CI | Фичи вычисляются (`eval`) без сборки тяжёлых пакетов (OPS-2) | AI-OPS-1 |

## 3. Контракты фич

### 3.1 `inference-service` (nixos, для хоста)

| ID | Правило |
|---|---|
| AI-INF-1 | Системный сервис; слушает **только** loopback по `my.ai.inference` (ML-3, NET-4). Аутентификации у сервиса нет: loopback доступен любому локальному процессу и пользователю; принято, т. к. секретов в сервисе нет (AI-A6 относится к шлюзу, секретам и командам). |
| AI-INF-2 | Предоставляет OpenAI-совместимый HTTP API и FIM-запросы (префикс + суффикс) для моделей соответствующего типа. |
| AI-INF-3 | Вычислительный бэкенд выбирается по `my.host.gpu.compute`. В фиче нет вендор-специфики вне реализации; хост без GPU получает CPU-вариант или отсутствие локальных ролей (ARCH-10, HOST-3). |
| AI-INF-4 | Набор локальных моделей определяется классом `my.host.gpu.vramGiB` (ML-3, раздел 5.1). Модели, не помещающиеся в ресурсы, не включаются без явной оговорки. |
| AI-INF-5 | Модели **выгружаются по таймауту простоя** (`my.ai.inference.keepAlive`). Постоянная резидентность допустима только по явному параметру хоста и запрещена на хостах с критерием A5. |
| AI-INF-6 | После suspend/hibernate/resume инференс работает **на GPU** без ручных действий (расширение A13). Известный отказ реализаций: после resume вычислительная библиотека теряет устройство, и сервис молча переходит на CPU. Фича MUST содержать (а) pre-sleep шаг: выгрузка моделей (`inference-release`) до сна — VRAM-состояние и контекст не переносятся через гибернацию; (б) post-resume шаг: перезапуск сервиса с переинициализацией модуля драйвера, отвечающего за вычислительную память. Реализация — P.3; подтверждение — AI-A5. |
| AI-INF-7 | Предоставляет команду `inference-release` в PATH системы: выгружает все модели через API, прав администратора не требует. |
| AI-INF-8 | Каталог моделей = `my.ai.inference.modelsDir`: **отдельный том вне политики снимков** (иначе модели попадают в снимки корня, STO-1) и вне бэкапа (STO-8); в persist-списке при эфемерном корне (STO-7). Собственных опций монтирования у тома нет (STO-1, L-11). |
| AI-INF-9 | Секретов нет. Сетевой исходящий доступ нужен только для загрузки моделей (п. 2.6). |
| AI-INF-10 | Список моделей задан декларативно. Если реализация загружает по изменяемому тегу, это фиксируется в Приложении P как принятое исключение из воспроизводимости. |
| AI-INF-11 | На хосте один инференс-бэкенд (ADR-20). |
| AI-INF-12 | Использование вычислительной платформы допускается только после подключения её бинарного кэша (ML-2, 3.7). |

### 3.2 Клиенты автодополнения и чата (редакторы)

Не отдельная фича: клиентская часть — каталог редактора в dotfiles (ARCH-15), пакеты — фича редактора (DEV-1).

| ID | Правило |
|---|---|
| AI-CMP-1 | FIM-запросы идут **напрямую** к `inference-service`; отдельного сервера автодополнения нет (ADR-20). |
| AI-CMP-2 | Для FIM используются модели «base»-типа; инструктивные варианты вставляют пояснения и разметку. |
| AI-CMP-3 | Клиент не блокирует ввод; при недоступности сервиса молчит (без ошибок в интерфейсе). |
| AI-CMP-4 | Адрес сервиса — из машинного слоя, иначе умолчание (DOT-13). |
| AI-CMP-5 | Автодополнение отключаемо на проект средствами редактора. |
| AI-CMP-6 | Горячие клавиши клиента не конфликтуют с механизмом автодополнения и сниппетов редактора; разрешает владелец конфига редактора. |
| AI-CMP-7 | Lock-файл плагинов клиента — в dotfiles (DOT-11). |
| AI-CMP-8 | Необязательные редакторы и IDE (вне реестра) MAY получать клиент. Их настройка — Nix (DOT-2) или собственные средства; MUST NOT ссылаться на бинарники, которых нет в PATH (DEV-9). |

### 3.3 `llm-gateway` (N+H, для пользователей с `ml`)

Назначение: **индирекция**. Агенты и редакторы обращаются к ролям (раздел 4); какая модель стоит за ролью — решает Nix по политике хоста. Благодаря этому dotfiles не содержат констант хоста (DOT-1, DOT-6).

| ID | Правило |
|---|---|
| AI-GW-1 | Пользовательский демон (user-юнит, тонкая обёртка над пакетом, DESK-4); только loopback; порт = `my.ai.gateway.portBase` + (uid − 1000); uid задан явно фичей `users` (стабильный номер: добавление пользователя не сдвигает порты остальных; имён в фиче нет — ARCH-17). ПРОВЕРИТЬ, что `users` фиксирует uid. |
| AI-GW-2 | Публикует роли раздела 4 как стабильные алиасы. Локальные бэкенды — из `my.ai.local`, облачные — данные фичи. |
| AI-GW-3 | Ключи провайдеров и ключ доступа — только из секретов пользователя через credentials; в конфиге плейсхолдеры (SEC-4, ML-5, USER-7). |
| AI-GW-4 | Все запросы требуют ключ доступа (защита от других локальных пользователей и процессов). |
| AI-GW-5 | **Fallback:** если облачная роль недоступна (нет туннеля, нет ключа, исчерпан лимит), запрос получает явную ошибку либо переводится на заранее заданную локальную роль с уведомлением. Тихая смена облачного провайдера запрещена. |
| AI-GW-6 | Лимиты расходов SHOULD задаваться на уровне шлюза. |
| AI-GW-7 | Содержимое запросов не логируется по умолчанию; журналы — локальные, в пользовательском каталоге состояния. |
| AI-GW-8 | Шлюз **вне реестра dotfiles**: конфиг непортативен (выводится из политики хоста и секретов), поэтому рендерится Nix — по аналогии с туннелем (A.6, DOT-2). |
| AI-GW-9 | Отсутствие облачных ключей не делает юнит `failed` (A4); локальные роли продолжают работать. |
| AI-GW-10 | SHOULD запускаться по требованию и останавливаться при простое (память ноутбука). |
| AI-GW-11 | Режим входа в приложение «по подписке» (OAuth) шлюз не обслуживает: лимиты и логи шлюза на него не распространяются. Это документированное ограничение. |
| AI-GW-12 | Доступ к шлюзу — только пользователям с capability `ml` (USER-5): ключ доступа выдан лишь им. |
| AI-GW-13 | Шлюз хранит все облачные ключи, поэтому он — критичное звено цепочки поставок. Пакет берётся из зафиксированного lock-файлом источника и собирается из исходников, а не ставится из реестра пакетов во время работы; в рантайме нет `pip install`, самообновления и загрузки плагинов. Обновление — только через `flake update` с просмотром разницы замыканий (OPS-3). Юнит шлюза работает с минимумом прав: доступ только к собственным credentials и каталогу состояния. Ключи провайдеров — отдельные, с лимитами расходов (AI-GW-6). Основание — инцидент марта 2026 (P.7). |

Фича владеет пакетами агентных CLI **и лаунчером-песочницей** (один владелец — SLOT-1; лаунчер и пакеты связаны, поэтому в одной фиче).

## 4. Словарь ролей моделей (контракт)

Роль — стабильное имя, которое используют dotfiles, редакторы и агенты. Какая модель стоит за ролью — решает Nix (локальные роли — политика VRAM, облачные — данные шлюза).

| Роль | Класс | Назначение | Потребители |
|---|---|---|---|
| `local-fast` | локальная | FIM-автодополнение | Клиенты редакторов |
| `local-chat` | локальная | Чат, объяснение; может отсутствовать на слабом хосте | Редакторы, контролируемый агент |
| `local-embed` | локальная | Эмбеддинги; только после гейта 8.3 | Условный L5 |
| `cost-autonomous` | облачная | Автономные задачи средней сложности | Альтернативный агент |
| `strong-autonomous` | облачная | Сложные задачи | Тяжёлый агент |
| `experimental` | любая | Эксперименты | Экспериментальные агенты |

| ID | Правило |
|---|---|
| AI-ROLE-1 | Имена ролей — публичный контракт между Nix и dotfiles. Переименование или смена смысла — ломающее изменение: тег dotfiles и запись в `REGISTRY.md` (DOT-10). |
| AI-ROLE-2 | Идентификаторы конкретных моделей и провайдеров в dotfiles **запрещены** (DOT-1, DOT-6). |
| AI-ROLE-3 | Если локальной роли на хосте нет (мало VRAM), шлюз отдаёт заранее заданный fallback или явную ошибку (AI-GW-5). |
| AI-ROLE-4 | Эксперименты в обход ролей допускаются только в режиме `offline` или отдельным ограниченным ключом. |

## 5. Ресурсы и совместное использование GPU

### 5.1 Политика по классу VRAM

Класс выбирается по `my.host.gpu.vramGiB` (ML-3). Конкретные модели — Приложение P.2.

| Класс VRAM | `local-fast` | `local-chat` |
|---|---|---|
| < 3 ГБ или `compute = none` | Малая модель на CPU либо отсутствует (редактор использует встроенные средства) | Отсутствует |
| 3–5 ГБ | Малая модель на GPU | Только при подтверждённой замером скорости; иначе — fallback в облако |
| 6–11 ГБ | Средняя | Средняя модель на GPU |
| ≥ 12 ГБ | Средняя | Крупная (после проверки) |

Пороги скорости и задержки (AI-A2) — целевые значения, подтверждаемые замером; фактические значения фиксируются в `docs/runbook.md`.

### 5.2 Простой и питание

| ID | Правило |
|---|---|
| AI-RES-1 | Одновременно в VRAM — не более одной FIM-модели; чат-модель никогда не конкурирует с FIM за VRAM (выгрузка или отдельное время жизни). Механизм: лимит одновременно загруженных моделей = 1 в конфигурации сервиса. GPU-задачи проектных окружений (ML-6, шаблон `ml-cuda`) делят те же 4 ГБ: они SHOULD вызывать `inference-release` перед стартом (по аналогии с играми, AI-RES-5). |
| AI-RES-2 | Время жизни модели в простое конечно (`my.ai.inference.keepAlive`). |
| AI-RES-3 | После выгрузки модели дискретная GPU должна вернуться в состояние suspended (A5). Подсистема не включает настроек, удерживающих GPU активной; их владелец — `hardware/*`. |
| AI-RES-4 | Эмбеддинги, если включены, считаются на CPU. |

### 5.3 Игры

| ID | Правило |
|---|---|
| AI-RES-5 | Во время игры дискретная GPU принадлежит игре. Подсистема предоставляет `inference-release` (AI-INF-7); вызывать её при старте игры SHOULD оптимизатор игр. |
| AI-RES-6 | Страховка независимо от хука: конечный `keepAlive` (AI-RES-2). |
| AI-RES-7 | Подсистема не изменяет конфигурацию и юниты игровых фич (FEAT-6, L-1). |

### 5.4 Гибернация, RAM, диск

| ID | Правило |
|---|---|
| AI-RES-8 | После трёх циклов hibernate/resume инференс загружает модель на GPU без ручных действий (A13). |
| AI-RES-9 | Состояние шлюза и агентов не требует гарантий на resume; процессы перезапускаются штатно. |
| AI-RES-10 | Бюджет RAM и диска (модели, замыкание вычислительной платформы, offload) описывается в `docs/runbook.md`. Каталог моделей вне бэкапа (STO-8). |

Отдельных «режимов машины» и команды их переключения подсистема не вводит: управление — конечным `keepAlive` и `inference-release`.

## 6. Модель угроз и доверие

**Активы:** секреты пользователя, ключи SSH/GPG, репозиторий конфигурации системы, домашние данные, профиль браузера.
**Угрозы:** (1) внедрение инструкций через содержимое репозиториев, веб и вывод инструментов; (2) деструктивные ошибки агента; (3) утечка секретов; (4) цепочка поставок (плагины, расширения, загрузка кода на лету).

Три уровня доверия; нижний уровень **не может ослабить** верхний:

| Уровень | Что | Кто владеет | Свойство |
|---|---|---|---|
| 0 — граница | Лаунчер, юниты, секреты, политика ресурсов | Nix | Жёстко; не редактируется из сеанса агента |
| 1 — настройки пользователя | Конфиги агентов и клиентов (dotfiles) | Пользователь | Умолчания; живая правка без пересборки (DOT-4) |
| 2 — проект | Инструкции, MCP и хуки проекта, маркеры | Автор проекта | Недоверенный ввод; может только ужесточать (AI-SBX-9) |

| ID | Правило |
|---|---|
| AI-SEC-1 | Граница безопасности — изоляция процесса и очистка окружения (AI-SBX-1…3, 6), а не перечни запрещённых слов. |
| AI-SEC-2 | Секреты агентам не передаются, кроме ключа доступа к шлюзу. |
| AI-SEC-3 | Репозиторий конфигурации системы агентам недоступен: изменение системной конфигурации — только человек. |
| AI-SEC-4 | Любое облачное обращение идёт через шлюз и туннель; прямые обращения агентов к провайдерам в обход шлюза не настраиваются (за исключением режима подписки, AI-GW-11). |
| AI-SEC-5 | Проект может включить `offline`, но не может включить облако или расширить права. |
| AI-SEC-6 | Рабочие проекты (корни по AI-SBX-5) по умолчанию `offline`; облако включается явным флагом, а не настройкой проекта (AI-SEC-5). |
| AI-SEC-7 | Журналы локальные, содержимое кода отключаемо (AI-GW-7, AI-AGT-7). |
| AI-SEC-8 | Секреты и приватные факты в репозитории, чате и документах — запрещены (SEC-5); ключи только в sops. |
| AI-SEC-9 | Отправка приватного кода провайдерам допускается только после явного решения владельца проекта; учитывать требования работодателя. |

### P.3 Эскиз фичи инференса (схематично; синтаксис проверить сборкой)

```nix
# modules/ai/inference-service-ollama.nix — класс nixos, для хоста (пресет nixos `ml`)
{ lib, ... }: {
  flake.modules.nixos.inference-service-ollama = { config, pkgs, ... }:
  let
    gpu = config.my.host.gpu;                          # vramGiB, compute
    pkg = { cuda = pkgs.ollama-cuda; vulkan = pkgs.ollama-vulkan; none = pkgs.ollama-cpu; }.${gpu.compute}; # ПРОВЕРИТЬ имена
    roles =
      if gpu.vramGiB >= 6 then { local-fast = "<tag-1.5b-base>"; local-chat = "<tag-7b>"; }
      else if gpu.vramGiB >= 3 then { local-fast = "<tag-1.5b-base>"; }
      else { };
  in {
    my.ai.local = roles;                               # читает llm-gateway (osConfig.my.ai.local)
    services.ollama = {                                # имена опций — ПРОВЕРИТЬ
      enable = true;
      package = pkg;
      host = config.my.ai.inference.host;
      port = config.my.ai.inference.port;
      loadModels = lib.attrValues roles;
      environmentVariables = {
        OLLAMA_KEEP_ALIVE = config.my.ai.inference.keepAlive;
        OLLAMA_MAX_LOADED_MODELS = "1";               # AI-RES-1
      };
    };
    environment.systemPackages = [ (pkgs.writeShellScriptBin "inference-release" ''
      # выгрузить все модели через API; права администратора не нужны
    '') ];

    # AI-INF-6: pre-sleep выгрузка, post-resume перезапуск (известный отказ — GPU теряется после resume)
    systemd.services.inference-pre-sleep = {
      before = [ "sleep.target" ]; wantedBy = [ "sleep.target" ];
      serviceConfig = { Type = "oneshot"; ExecStart = "/run/current-system/sw/bin/inference-release"; };
    };
    systemd.services.inference-post-resume = {
      after = [ "suspend.target" "hibernate.target" "hybrid-sleep.target" "suspend-then-hibernate.target" ];
      wantedBy = [ "suspend.target" "hibernate.target" "hybrid-sleep.target" "suspend-then-hibernate.target" ];
      serviceConfig.Type = "oneshot";
      script = ''
        systemctl stop ollama.service
        ${pkgs.kmod}/bin/rmmod nvidia_uvm || true       # вендор-специфика допустима только здесь (AI-INF-3)
        ${pkgs.kmod}/bin/modprobe nvidia_uvm
        systemctl start ollama.service
      '';                                              # ПРОВЕРИТЬ порядок юнитов и имена целей
    };
  };
}
```

Выгрузка модели на практике — запрос к API с нулевым временем жизни (`keep_alive: 0`) для каждой загруженной модели. Отказ после resume (потеря GPU, откат на CPU) описан в официальной документации Ollama; штатный обход — перезагрузка модуля `nvidia_uvm`, что и делает `inference-post-resume`.

### P.6 Отклонённые реализации

Upstream — v0.32.0 (январь 2026), последующих релизов не найдено; проект смещает фокус на облачный продукт.
- Диагностика, выполненная ранее, верна по сути; уточнения: `rust-bin` относится к внешнему оверлею, а не к nixpkgs; пакет из закреплённого старого nixpkgs **нарушает ARCH-14** (второй экземпляр основного канала), а оверлеи тулчейнов Rust допустимы только как inputs шаблонов проектов (раздел 3 Архитектуры) — поэтому «старый Rust» как путь не подходит и в принципе.
- Помимо этого: свой процесс инференса рядом с общим — конфликт за 4 ГБ VRAM (нарушение ADR-20).
- Вернуться можно при условиях: снят `broken`, сборка воспроизводима без ручных патчей, есть потребность в серверном решении для команды, оно запускается не на хосте с малым VRAM.

**Отклонено также:** собственный роутер (вместо шлюза), собственный индексатор и векторный поиск до гейта, отдельный пользователь-песочница (ARCH-17: пользователи — данные), хуки игры внутри фичи инференса (FEAT-6).

# Архитектура NixOS-систем — нормативный документ

> Версия 2.1 · 2026-10-08 · Статус: действующий (изменения 2.1 — Приложение R)
> **Нормативная часть (разделы 0–22)** не содержит имён конкретных пользователей, программ, версий и железа (кроме инструментов каркаса, раздел 3 и ARCH-20): это общие принципы, контракты и правила.
> **Приложение A** — информативный профиль первой реализации (конкретные программы, железо, особенности). Меняется без ADR и не является архитектурой.
> Документ не содержит секретов и приватных фактов (раздел 9). Наследие не учитывается: описана целевая система «с нуля».

---

## 0. Как пользоваться документом

### 0.1 Для LLM-ассистента (читать первым)

1. **MUST / MUST NOT / SHOULD / MAY** — в смысле RFC 2119. У правил есть ID (`ARCH-3`, `DOT-5`, …) — ссылайтесь на них.
2. Любое предложение (код, пакет, файл) начинайте с указания: **слот или фича**, **путь файла**, **класс** (`nixos` / `homeManager` / `dotfiles`) и **для кого** (хост / пользователь).
3. Нормативная часть не называет конкретные программы, версии, имена пользователей и модели железа. Конкретные выборы — в Приложении A; если пользователь меняет выбор (другой композитор, другой редактор), меняется **реализация слота** и каталог в dotfiles — контракты и остальные фичи остаются (ARCH-16).
4. Если запрос противоречит документу — скажите об этом, процитируйте ID правила и предложите вариант в рамках правил либо запись в реестр ADR (раздел 21). Молча нарушать правила нельзя.
5. Не выдумывайте имена опций NixOS / Home Manager, пакетов и flake-inputs выбранного релиза. Если не уверены — пометьте `ПРОВЕРИТЬ` и дайте команду проверки (`nix eval`, `nixos-option`, поиск по исходникам).
6. Секреты и приватные факты — только плейсхолдеры `<SECRET>`. Не копируйте значения из чата в код (раздел 9).
7. Стиль: идентификаторы и пути — английские; комментарии и документация — русские; форматирование — единым форматтером проекта.
8. Формат ответа с изменениями: список файлов, полное содержимое новых/изменённых файлов (или unified diff с путями), затем «как проверить» (команды) и критерий приёмки.
9. Временных обходов и «потом перенесём» нет: каждый артефакт сразу кладётся в целевое место (ARCH-19).

### 0.2 Для человека

- Разделы 18 (чек-листы) и 20 (план и трекер) — рабочие; трекер обновляйте.
- Изменение принципов, каркаса, секретов, хранилища, сети — только через ADR (раздел 21).
- Всё конкретное и сменяемое живёт в Приложении A.

## 1. Контекст и цели

**Класс систем:** персональные рабочие станции и ноутбуки на NixOS (плюс вспомогательные хосты). Один репозиторий описывает все хосты и всех пользователей.

**Цели (в порядке приоритета):**
1. Воспроизводимость и откатываемость любого состояния системы.
2. Модульность: добавить/убрать возможность = добавить/убрать строку в композиции.
3. Сменяемость реализаций: любая прикладная роль (композитор, панель, терминал, редактор, шелл, туннель-клиент …) заменяется без пересмотра архитектуры.
4. Многопользовательность: N ≥ 1 пользователей с разными возможностями на одном хосте и между хостами.
5. Переносимость между железом: один репозиторий — несколько хостов с разным оборудованием; установка на новую машину по чек-листу.
6. Переносимость пользовательских конфигов приложений на другие дистрибутивы.
7. Безопасность при публичном репозитории.
8. Гибернация как обязательная возможность мобильных хостов.

**Прикладные домены:** разработка; офис и коммуникации; медиа и игры; ML и агенты.

**Допущения среды:** репозитории публичны; внешний трафик может требовать туннелирования; сеть может быть нестабильной или ограниченной.

**Вне охвата:** управление не-NixOS системами, облачные деплои.

## 2. Корневые принципы

| ID | Правило |
|---|---|
| ARCH-1 | Единица модульности — **фича** (одна задача). Один файл = одна фича = один владелец. Файл фичи содержит все её классы (`nixos`, `homeManager`). |
| ARCH-2 | Каждый `.nix` в `modules/` — flake-parts-модуль, подхватываемый автоимпортом. Файлы и каталоги с префиксом `_` игнорируются (черновики, шаблоны). Не-flake-parts файлы (например сгенерированное железо) лежат **вне** `modules/`. |
| ARCH-3 | Фичи **не импортируют друг друга**. Зависимости выражаются составом пресета или хоста. |
| ARCH-4 | Хост — композиция + факты (`my.host.*`), без пакетов, сервисов и логики. Пользователь — запись данных + возможности (`my.users.*`). |
| ARCH-5 | Каждый факт определён **ровно один раз**: пакет, переменная окружения, раскладка, палитра, порты прокси, параметры железа. Перед добавлением — поиск, что дубля нет. |
| ARCH-6 | Включение — композицией. Опции `my.*` — только для параметров. Не создавать `enable`-опцию ради включения фичи. |
| ARCH-7 | `nixos`-класс настраивает систему, `homeManager` — пользователя. Связь — через реестр пользователей и их `capabilities` (раздел 5.2). |
| ARCH-8 | `specialArgs` / `extraSpecialArgs` — не транспорт значений. Значения идут через внешний `config.my.*` и NixOS-опции `my.host.*`. |
| ARCH-9 | Тулчейны разработки (компиляторы, интерпретаторы, SDK, вычислительные платформы) — в проектных окружениях. В системе — только редакторы, VCS, контейнерный рантайм, запасные LSP. |
| ARCH-10 | Железо — отдельный слой (`hardware/*`, `my.host`, сгенерированное описание машины). Общие фичи не знают о конкретном оборудовании. |
| ARCH-11 | Нет файлов-свалок (`packages.nix`, `common/`, `misc.nix`). Пакет принадлежит фиче, которая его использует. Пользовательские — `home.packages`; `environment.systemPackages` — только для нужд системы и сервисов. |
| ARCH-12 | Файл фичи ≲ 150 строк; больше — делить. |
| ARCH-13 | `lib.mkForce`, `lib.mkOverride`, `rec`, `with` на больших областях — только с комментарием-обоснованием. |
| ARCH-14 | Основной канал пакетов один (стабильный релиз) + нестабильный канал **точечно**. Второй экземпляр основного канала или Home Manager в lock-файле — дефект (у всех inputs `follows`). |
| ARCH-15 | **Содержимое конфигов приложений принадлежит dotfiles, а не Nix** (раздел 8). Nix владеет пакетами, юнитами, сессией, секретами, железом. |
| ARCH-16 | **Слоты и сменные реализации.** Прикладная роль описывается как *слот* с контрактом (раздел 6); конкретная программа — *реализация слота*. Замена реализации не меняет контракты и остальные фичи: заменяются фича-реализация и каталог dotfiles. Имена `<слот>-<реализация>` — только в именах фич, не в нормативных правилах. |
| ARCH-17 | **Пользователи — данные, не код.** В фичах нет имён пользователей. Система поддерживает N ≥ 1 пользователей; каждый описан записью в `my.users`. |
| ARCH-18 | **Нет привязки к версиям.** Нормативная часть не содержит номеров версий; версии фиксируются lock-файлами и профилем реализации (Приложение A). |
| ARCH-19 | **Без наследия и временных обходов.** Каждый артефакт — в целевом месте целевой структуры. |
| ARCH-20 | **Инструменты каркаса** (раздел 3: flake, flake-parts, import-tree, Home Manager, sops-nix, disko, treefmt-nix и т. п.) — часть самой архитектуры, а не сменная реализация слота: они могут называться в нормативной части и в `flake.nix`; ARCH-16/ARCH-18 на них не распространяются. Замена инструмента каркаса — только через ADR. |

## 3. Каркас: роли и инструменты

| Роль | Реализация | Правило |
|---|---|---|
| Ядро конфигурации | flake + lock-файл | lock в git; обновление осознанное (OPS-3) |
| Модульный каркас | flake-parts (с модулем `modules`) | ARCH-2 |
| Автоимпорт | import-tree | префикс `_` исключает файл |
| Пользовательское окружение | Home Manager как NixOS-модуль | ветка того же релиза, что и основной канал |
| Секреты | sops-nix (age) | раздел 9 |
| Разметка дисков | disko | раздел 10 |
| Формат и линт | treefmt-nix (форматтер Nix, statix, deadnix) | OPS-1 |
| Профили железа | nixos-hardware (если есть для модели) | HOST-2 |
| Эфемерное состояние (опц.) | impermanence | STO-7 |
| Канал пакетов | стабильный релиз; нестабильный — точечно через overlay с комментарием-причиной | ARCH-14 |

Ссылки и версии — только в `flake.nix` и `flake.lock`. Источники тулчейнов языков (оверлеи и т. п.) — inputs **шаблонов проектов**, не системы.

## 4. Структура репозитория

```
nixos-config/                        # публичный репозиторий, чистая история
├── flake.nix  flake.lock
├── modules/                         # ТОЛЬКО flake-parts-модули
│   ├── core/                        #   каркас: flake-parts, treefmt, checks, объявление my.*
│   ├── users/                       #   записи пользователей (данные): <имя>.nix
│   ├── base/                        #   nix-settings, locale-keyboard, users, hm, fonts, host-facts
│   ├── hardware/                    #   gpu-*, power, sleep, audio, bluetooth, automount, firmware
│   ├── storage/                     #   разметка, swap, обслуживание, бэкап, эфемерное состояние
│   ├── security/                    #   sops, ssh, hardening, firewall
│   ├── network/                     #   менеджер сети, dns, tunnel-<реализация>, killswitch
│   ├── desktop/                     #   слоты рабочего стола (раздел 6)
│   ├── shell/                       #   shell-<реализация>, vcs-tools, env-manager, terminal-*, dotfiles-link
│   ├── dev/                         #   editor-<реализация>, lsp-global, containers, databases
│   ├── office/  media/  gaming/  ai/
│   ├── presets/                     #   пресеты (nixos — для хоста, homeManager — по capability)
│   └── hosts/                       #   <хост>.nix, _template.nix (игнорируется)
├── machines/<хост>/hardware.nix     # НЕ flake-parts: сгенерированное железо, без логики
├── secrets/                         # зашифрованные sops-файлы: common, hosts/<хост>, users/<имя>
├── .sops.yaml                       # только публичные recipients
├── templates/                       # шаблоны проектов (по одному на поддерживаемый язык/стек)
├── docs/                            # README, runbook, adr/
├── justfile                         # bootstrap, rebuild, dotfiles-clone, add-host, hibernate-offset
└── .github/workflows/               # CI
```

Отдельный публичный репозиторий **dotfiles** (раздел 8):

```
dotfiles/
├── <приложение>/ …                  # по каталогу на приложение из реестра
├── REGISTRY.md                      # реестр портативных приложений и их версионные заметки
├── theme/palette.toml  theme/gen/   # единственный источник палитры; генератор colors.*
├── machine.d.example/               # заглушки машинного слоя
├── install.sh                       # symlink'и + заглушки; --check-deps для других дистрибутивов
└── README.md
```

## 5. Контракт фичи, пользователи и namespace `my.*`

### 5.1 Правила фичи

| ID | Правило |
|---|---|
| FEAT-1 | Имя — `kebab-case`, совпадает с именем файла; домен — в пути. Реализации слота: `<слот>-<реализация>`. |
| FEAT-2 | Фича объявляет `flake.modules.<класс>.<имя>`; классы: `nixos`, `homeManager`. |
| FEAT-3 | Параметры — из `config.my.*` (внешний scope), `config.my.host.*` (nixos), `osConfig.my.host.*` (HM). Жёстких значений хоста нет. |
| FEAT-4 | Имён пользователей в фичах нет (ARCH-17). Системные интеграции «на пользователя» — только по `capabilities`. |
| FEAT-5 | Пресет — фича, содержащая только `imports` (в каждом классе перечисляются лишь фичи, у которых этот класс есть). |
| FEAT-6 | Конфликт определений решается в фиче-владельце, а не `mkForce` в хосте. |
| FEAT-7 | Новая фича MUST попасть в каталог (раздел 6) в том же изменении. |
| FEAT-8 | Каждая фича включена хотя бы в один пресет или хост; неиспользуемая фича — дефект (проверка в CI, OPS-2). |

### 5.2 Пользователи и возможности

| ID | Правило |
|---|---|
| USER-1 | Источник истины — `my.users.<имя>` (внешний scope; файл `modules/users/<имя>.nix`): `admin`, `capabilities`, источник dotfiles. Приватные факты пользователя — только в sops (SEC-2). |
| USER-2 | Хост выбирает подмножество: `my.host.users`. Один пользователь может быть на нескольких хостах, на хосте — несколько пользователей. |
| USER-3 | Фича `users` создаёт системные учётные записи (администратор → группа администрирования) и подключает HM-модули: для каждой capability `c` — модуль `flake.modules.homeManager.<c>`, если он существует. |
| USER-4 | **Capability — архитектурный словарь:** `desktop`, `development`, `office`, `media`, `gaming`, `ml`, `containers`, … Новое слово — запись в каталог (раздел 6). Одно слово может иметь nixos-пресет (для хоста) и homeManager-пресет (для пользователя) с одинаковым именем. |
| USER-5 | Системные интеграции на пользователя (группы доступа, лимиты, права на устройства) применяются к пересечению `my.host.users` ∩ «пользователи с capability». |
| USER-6 | HM-класс не пишет в чужие home; общее — через nixos-класс. |
| USER-7 | У пользователя свои секреты, свой ключ и свой источник dotfiles (SEC-7, DOT-4). Имена пользователей — публичные данные, не использовать в них приватные идентификаторы. |

### 5.3 Опции `my.*`

| Опция | Уровень | Назначение |
|---|---|---|
| `my.users.<имя>.admin` | внешний | права администратора |
| `my.users.<имя>.capabilities` | внешний | список возможностей (USER-4) |
| `my.users.<имя>.dotfiles.source` | внешний | путь к рабочей копии dotfiles пользователя (`null` — симлинки не создаются, DOT-4) |
| `my.theme.palette` | внешний | палитра (читается из dotfiles, DOT-9) |
| `my.host.name`, `my.host.class` | nixos | имя и класс хоста (`laptop`, `workstation`, `server`, `vm`) |
| `my.host.stateVersion` | nixos | версия состояния, **параметр хоста** (раздел 7) |
| `my.host.users` | nixos | список пользователей хоста |
| `my.host.gpu.{integratedBusId,discreteBusId,vramGiB}` | nixos | шины и объём памяти GPU (если есть) |
| `my.host.battery`, `my.host.inputDevices`, `my.host.outputs` | nixos | факты для компонентов рабочего стола |
| `my.host.disk.device`, `my.host.resume.offset` | nixos | диск для разметки; смещение swap-файла для гибернации |
| `my.tunnel.local.{http,socks}` | nixos | loopback-адреса локального режима туннеля (не секрет); объявляет фича `tunnel-facts` (как и остальные `my.tunnel.*`, VPN_SUBSYSTEM 2.3) |

Секретные и приватные значения в `my.*` **не** хранятся (раздел 9).

### 5.4 Скелеты (схематично; синтаксис проверить сборкой)

`flake.nix`:

```nix
{
  inputs = {
    nixpkgs.url          = "github:nixos/nixpkgs/<стабильный-релиз>";
    nixpkgs-unstable.url = "github:nixos/nixpkgs/nixos-unstable";
    flake-parts.url      = "github:hercules-ci/flake-parts";
    import-tree.url      = "<актуальный адрес проекта>";
    home-manager = { url = "github:nix-community/home-manager/<ветка-релиза>"; inputs.nixpkgs.follows = "nixpkgs"; };
    sops-nix     = { url = "github:Mic92/sops-nix";      inputs.nixpkgs.follows = "nixpkgs"; };
    disko        = { url = "github:nix-community/disko"; inputs.nixpkgs.follows = "nixpkgs"; };
    treefmt-nix  = { url = "github:numtide/treefmt-nix"; inputs.nixpkgs.follows = "nixpkgs"; };
    dotfiles     = { url = "<репозиторий dotfiles>"; flake = false; };   # читает theme/palette.toml (DOT-9); симлинки ~/.config идут не через этот input, а на путь из dotfiles.source (DOT-4)
  };
  outputs = inputs:
    inputs.flake-parts.lib.mkFlake { inherit inputs; } (inputs.import-tree ./modules);
}
```

Объявление реестра (`modules/core/options.nix`):

```nix
{ lib, ... }: {
  options.my.users = lib.mkOption {
    default = { };
    type = lib.types.attrsOf (lib.types.submodule {
      options = {
        admin        = lib.mkOption { type = lib.types.bool;                default = false; };
        capabilities = lib.mkOption { type = lib.types.listOf lib.types.str; default = [ ]; };
        dotfiles.source = lib.mkOption { type = lib.types.nullOr lib.types.str; default = null; };
      };
    });
  };
}
```

Запись пользователя (`modules/users/alice.nix`, имя — плейсхолдер):

```nix
{ ... }: {
  my.users.alice = {
    admin = true;
    capabilities = [ "desktop" "development" "office" ];
    dotfiles.source = "/home/alice/dotfiles";
  };
}
```

Фича `users` (создание учётных записей и подключение HM по capabilities):

```nix
{ config, lib, ... }:
let outer = config; in {                        # outer — внешний (flake-parts) config
  flake.modules.nixos.users = { config, ... }:  # здесь config — NixOS
  let
    hostUsers = lib.getAttrs config.my.host.users outer.my.users;
    hm = outer.flake.modules.homeManager;
  in {
    users.users = lib.mapAttrs (_: u: {
      isNormalUser = true;
      extraGroups = lib.optional u.admin "wheel";
    }) hostUsers;
    home-manager.users = lib.mapAttrs (_: u: {
      imports = lib.concatMap (c: lib.optional (lib.hasAttr c hm) hm.${c}) u.capabilities;
    }) hostUsers;
  };
}
```

Системная интеграция «на пользователя» по capability (`modules/dev/containers.nix`):

```nix
{ config, lib, ... }:
let
  outer = config;
  withCap = cap: lib.attrNames (lib.filterAttrs (_: u: lib.elem cap u.capabilities) outer.my.users);
in {
  flake.modules.nixos.containers = { config, ... }:
  let users = lib.intersectLists config.my.host.users (withCap "containers"); in {
    # включение рантайма контейнеров — реализация слота (Приложение A)
    users.users = lib.genAttrs users (_: { extraGroups = [ "<группа-рантайма>" ]; });
  };
}
```

Пресет с двумя классами (`modules/presets/desktop.nix`):

```nix
{ config, ... }:
let n = config.flake.modules; in {
  flake.modules.nixos.desktop       = { imports = with n.nixos;       [ /* session-<реализация>, display-manager-<реализация>, theme, … */ ]; };
  flake.modules.homeManager.desktop = { imports = with n.homeManager; [ /* bar-<реализация>, notifier-<реализация>, launcher-<реализация>, … */ ]; };
}
```

Хост (`modules/hosts/example-host.nix`):

```nix
{ config, inputs, ... }:
```

## 6. Каталог слотов и фич

Классы: **N** — nixos, **H** — homeManager. *Слот* — роль с контрактом; реализация именуется `<слот>-<реализация>` (ARCH-16). Конкретные реализации — Приложение A.

**base:** `nix-settings` (N: flakes, доверенные пользователи, GC, оптимизация store одним механизмом, substituters), `locale-keyboard` (N: TZ, i18n, консоль, раскладки — единственный источник), `users` (N: USER-3), `hm` (N: подключение Home Manager; `useGlobalPkgs` и `useUserPackages` включены — один экземпляр nixpkgs с общими overlay и `allowUnfree`, ARCH-14), `fonts` (N: шрифты системы и метрически совместимые офисные), `host-facts` (N: объявление `my.host.*`).

**hardware:** `gpu-integrated` (N: аппаратное ускорение видео), `gpu-discrete` (N: драйвер, управление питанием, сохранение состояния для сна), `gpu-hybrid` (N: рендер на дискретной по запросу, стабильные идентификаторы устройств), `power` (N: энергосбережение, политика закрытия крышки и низкого заряда), `sleep` (N: параметры resume), `audio`, `bluetooth`, `automount`, `firmware`.

**storage:** `layout` (N: декларативная разметка по `my.host.disk.device`), `swap` (N: swap-файл под гибернацию), `maintenance` (N: проверки целостности), `backup` (N), `ephemeral-root` (N, опционально).

**security:** `sops`, `ssh`, `hardening`, `firewall` (все N).

**network:** `network-manager`, `dns-resolver`, `vpn-client` (корпоративные/штатные VPN), `tunnel-<реализация>` (слот), `tunnel-facts` (N: объявление `my.tunnel.*`), `tunnel-server-<реализация>` (N, опц. — декларативный выход, VPN_SUBSYSTEM 4.6), `killswitch` (все N).

**desktop (слоты):** `session-<р>`, `display-manager-<р>`, `bar-<р>`, `notifier-<р>`, `launcher-<р>`, `lockscreen-<р>`, `idle-<р>`, `wallpaper-<р>`, `screenshot-<р>`, `clipboard-<р>`, `polkit-agent-<р>`, `osd-<р>`, `theme` (N+H: GTK/Qt/курсор/иконки, палитра для Nix-владеемых потребителей).

**shell:** `shell-<р>` (N+H), `vcs-tools` (H), `env-manager` (N: автоактивация проектных окружений, слой совместимости для динамических бинарников), `terminal-<р>` (H), `file-manager-<р>` (H), `dotfiles-link` (N+H: раздел 8).

**dev:** `editor-<р>` (N+H), `lsp-global` (H), `containers` (N+H), `databases` (H), `api-tools` (H, опц.).

**office / media / gaming / ai:** `office-suite`, `mail-calendar`, `documents`, `communication`, `print-scan` (опц.); `video-player`, `browser`, `torrent`; `game-platform`, `compat-layer`, `game-optimizer`, `overlay`; `compute-cache`, `inference-service-<р>` (слот), `container-gpu`, `agents-tools`; подсистема ML добавляет `ai-facts`, `llm-gateway`, `code-context` (AI_SUBSYSTEM 2.2).

**Пресеты хоста (nixos):** `base`, `laptop`, `workstation`, `server`, `vm` — по классу хоста; `<capability>` — системная часть возможности; `tunnel` — сетевая среда хоста (не capability, VPN_SUBSYSTEM ADR-25).
**Пресеты пользователя (homeManager):** имена совпадают с capability (`desktop`, `development`, `office`, `media`, `gaming`, `ml`, `containers`).

### Контракты ключевых слотов

| Слот | Контракт (минимум) |
|---|---|
| `session` | Регистрируется у менеджера входа; запускается через менеджер сессий с интеграцией в systemd user; предоставляет `graphical-session.target`; порталы (захват экрана, диалоги); **один** механизм экспорта окружения; хостовые параметры (устройства, мониторы, раскладка) — через машинный слой; конфиг композитора — каталог в dotfiles. На хосте может быть установлено несколько реализаций, активная выбирается при входе. |
| `display-manager` | Предлагает сессии установленных `session`; тема из палитры. |
| `tunnel` | Раздел 11. |
| `shell` | Регистрируется в системе; каталог конфигурации сообщает **система** (DOT-12), не конфиг; плагины/фреймворки — пути из машинного слоя; хук `env-manager` — в dotfiles. |
| `editor` | Пакет и провайдеры; запасные LSP/форматтеры/отладчики — `lsp-global`; менеджер плагинов с lock-файлом в dotfiles (DOT-11); переменная редактора по умолчанию определена **только здесь**. |
| `terminal`, `file-manager` | Пакет; конфиг — dotfiles; цвета из палитры. |
| `env-manager` | Автоактивация проектных окружений с кэшем; интеграция с шеллом — в dotfiles (системная интеграция отключена, чтобы не было двух хуков). |

**SLOT-1** Реализация слота — одна фича: владеет пакетом, юнитом (если демон), системной интеграцией; конфиг — в dotfiles.
**SLOT-2** Не более одной активной реализации слота на пользователя (`session` — см. выше).
**SLOT-3** Реализации взаимозаменяемы: замена затрагивает только фичу-реализацию, пресет и каталог dotfiles.
**SLOT-4** Компоненты оболочки рабочего стола (`bar`, `notifier`, `launcher`, `lockscreen`, `idle`, `wallpaper`, `screenshot`, `clipboard`, `polkit-agent`, `osd`): (a) демон — user-юнит, привязанный к `graphical-session.target`; (b) значения хоста — из машинного слоя; (c) цвета — из палитры; (d) адаптеры композитора (рабочие столы, IPC, раскладка) вынесены в отдельные файлы конфигурации в dotfiles и подключаются штатным include.

## 7. Хосты

| Класс | Назначение | Состав (пресеты) |
|---|---|---|
| `laptop` | мобильный; батарея, гибернация, шифрование диска | `base laptop` + capabilities |
| `workstation` | стационарный | `base workstation` + capabilities |
| `server` | headless, без рабочего стола | `base server` |
| `vm` | **проверка переносимости**, собирается в CI | `base` + минимальный набор |

| ID | Правило |
|---|---|
| HOST-1 | Хост-файл `modules/hosts/<имя>.nix` = композиция + `my.host.*`. Шаблон — `_template.nix`. |
| HOST-2 | `machines/<имя>/hardware.nix` генерируется, без логики; профиль `nixos-hardware` подключается, если есть. |
| HOST-3 | Аппаратные различия выражаются составом (какие `hardware/*` подключены) и `my.host`. Общие фичи не содержат вендор-специфики. |
| HOST-4 | Хост класса `vm` MUST собираться в CI — доказательство, что общие фичи не завязаны на конкретное железо. |
| HOST-5 | **`my.host.stateVersion` — параметр хоста.** Задаётся при установке, не обязан совпадать с релизом канала; меняется осознанно — по заметкам к релизу, для сервисов с состоянием. Это не архитектурный запрет и не часть общего кода. Версия состояния HM по умолчанию берётся из неё. |
| HOST-6 | Новый хост — по чек-листу 18.3; у каждого хоста свой ключ sops (SEC-7). |
| HOST-7 | Параллельная установка на другое железо независима; общее — репозитории и ключи пользователей. |

## 8. Dotfiles-слой (пользовательские конфиги в `~/.config`)

**Цель:** конфиги приложений лежат в `~/.config`, правятся там же без пересборки и переносятся на другие дистрибутивы как есть.

**Граница владения.** Nix владеет тем, что перенести нельзя: пакеты и зависимости, systemd-юниты, сессия, секреты, железо, PAM, переменные окружения сессии, машинный слой. Dotfiles владеют **содержимым конфигов** приложений из реестра.

| ID | Правило |
|---|---|
| DOT-1 | Репозиторий dotfiles — отдельный, публичный, самодостаточный: без секретов, без путей `/nix/store`, без констант хоста. |
| DOT-2 | **Реестр портативных приложений** ведётся в `dotfiles/REGISTRY.md` (с версионными заметками). Добавление приложения — запись в реестр + ADR-lite. Приложение вне реестра конфигурируется Nix. |
| DOT-3 | Для приложений реестра Nix **не использует**: генераторы конфигов (`programs.<app>.settings`, `extraConfig`, `theme`, `services.<app>` с конфигом), `xdg.configFile.<app>`, `home.file` на файлы приложения. **Разрешено:** пакет, systemd-юнит демона, PAM/сессия, файлы машинного слоя. |
| DOT-4 | Для каждого пользователя `~/.config/<app>` — симлинк (`mkOutOfStoreSymlink`) на рабочую копию по пути `my.users.<имя>.dotfiles.source`. Правка видна без пересборки. Пока источник не указан или по пути ничего нет — симлинки этого приложения не создаются (fail-soft, как DOT-5), а не падает активация. Один механизм, без отдельного «read-only» режима. |
| DOT-5 | **Машинный слой** — единственное, что Nix кладёт рядом: `~/.config/machine.d/*` (реальный каталог, не симлинк на репозиторий; не коммитится в dotfiles). Портативные конфиги подключают его штатными include и MUST работать, если файла нет или он пуст. Если у приложения нет include — не-секретные и не-машинные значения лежат прямо в dotfiles. |
| DOT-6 | В машинный слой попадает: пути к фреймворкам и плагинам, устройства/мониторы/раскладка, имя батареи, префикс запуска приложений (зависит от менеджера сессий), цвета из палитры, переменные окружения шеллов. |
| DOT-7 | Переменные окружения **графической сессии** задаёт один механизм менеджера сессий, генерируемый Nix; без дублей в конфиге композитора и в HM `sessionVariables`. |
| DOT-8 | `install.sh` (для не-Nix систем): создаёт симлинки и заглушки машинного слоя; `--check-deps` печатает список пакетов для менеджеров пакетов других дистрибутивов. |
| DOT-9 | Палитра — только `theme/palette.toml`; генератор создаёт `colors.*` для каждого приложения (результат коммитится); Nix читает тот же TOML для своих потребителей. Новое значение палитры доходит до Nix-потребителей через `nix flake update <dotfiles-input>`. |
| DOT-10 | Конфиги ПО, чей синтаксис меняется между версиями, переносимы только в пределах совместимых версий. Целевая версия — в `REGISTRY.md`; ломающее изменение — тег репозитория. |
| DOT-11 | Приложения с собственным менеджером плагинов: lock-файл плагинов лежит в dotfiles (воспроизводимость). |
| DOT-12 | Приложения, находящие конфиг через переменную окружения: переменную задаёт система (не конфиг); на других системах — `install.sh`. |
| DOT-13 | Значения по умолчанию в портативных конфигах пишутся как «значение окружения, иначе умолчание»: значение, заданное системой, приоритетнее. |
| DOT-14 | Проверки: CI dotfiles (линтеры и валидаторы форматов); CI nixos-config (нет генераторов для приложений реестра, нет `/nix/store` в dotfiles). |

**Цена (принята осознанно):** откат поколения NixOS не откатывает конфиги приложений — откат через git dotfiles; версии ПО на разных дистрибутивах различаются — фиксируются в `REGISTRY.md`.
Не переносится по природе (остаётся в Nix): тема менеджера входа, GTK/Qt/dconf, systemd-юниты, sops, железо.

## 9. Секреты и публичный репозиторий

| ID | Правило |
|---|---|
| SEC-1 | Репозитории публичны: всё, что попало в git, считается раскрытым навсегда (включая историю). |
| SEC-2 | Классы данных: **A** — секрет (ключи, идентификаторы и адреса туннеля, API-ключи, пароли) → sops; **B** — приватные факты (личный e-mail, город, имена в домашней сети) → sops или обобщить; **C** — публичное (маршрутизация, палитра, имена пакетов, имена пользователей) → открыто; **D** — не в репозиторий вообще (SSH-приватные ключи, мастер-ключи, файлы ключей age). |
| SEC-3 | Секреты класса A — только sops. Значения зашифрованы; имена ключей YAML видны — называть нейтрально. |
| SEC-4 | Конфиги с секретами рендерятся шаблонами при активации, права 0400, сервису выдаются через механизм credentials. В `/nix/store` попадают только плейсхолдеры. |
| SEC-5 | **Запрещено** в репозитории, коде и чате: идентификаторы клиентов, адреса серверов, ключи, пароли, токены, личный e-mail, город, имена домашней сети. В примерах — `<SECRET>`. |
| SEC-6 | `.gitignore` содержит: файлы ключей, `result*`, каталоги окружений, `.env*`. |
| SEC-7 | Recipients в `.sops.yaml` (только публичные): ключ каждого пользователя (гибридный постквантовый, если поддерживает используемая версия инструмента) + ключ каждого хоста (из SSH-ключа хоста). Секреты пользователя — в отдельном файле; recipients: его ключ + ключи хостов, где он есть. |
| SEC-8 | В репозитории — только **ротируемые** секреты. Долгоживущие (SSH-ключи, мастер-ключи) — вне репозитория. Исключение: закрытый ключ собственного выхода туннеля допускается в sops как ротируемый, если процедура ротации описана в runbook (VPN_SUBSYSTEM, 6.3). |
| SEC-9 | Защита от утечек: pre-commit сканер секретов, защита push на хостинге, проверка в CI. |
| SEC-10 | Git-идентичность в публичных коммитах — анонимизированный адрес хостинга. |
| SEC-11 | Репозиторий начинается с чистой истории; секреты, когда-либо бывшие в публичном доступе, считаются скомпрометированными и заменяются. |
| SEC-12 | Установка/новый хост: ключ хоста MUST быть доставлен до первой активации, иначе секреты не расшифруются. |
| SEC-13 | Ключи входят в бэкап (STO-8): потеря ключа = потеря секретов. |

Раскладка: `secrets/common.yaml`, `secrets/hosts/<имя>.yaml`, `secrets/users/<имя>.yaml`. Эскейп-хэтч (не по умолчанию): приватный репозиторий секретов как flake-input.

## 10. Хранилище, загрузка, гибернация, состояние

| ID | Правило |
|---|---|
| STO-1 | Разметка декларативная (`layout`) и параметризована `my.host.disk.device`. Файловая система со снимками; раздельные тома по назначению: корень, пользовательские данные, хранилище пакетов, логи, снимки, swap, данные сервисов вне снимков и бэкапа — кэши и хранилище моделей (+ постоянное хранилище при эфемерном корне). Опции, действующие на всю файловую систему, задаются единообразно (не «по томам»). |
| STO-2 | Шифрование диска — MUST для классов `laptop`/`workstation` при новой установке. Разблокировка аппаратным модулем — MAY. |
| STO-3 | Загрузчик и initrd — по ADR; initrd на systemd (в 26.05 — по умолчанию, scripted-вариант удаляется в 26.11; нужен для декларативного отката корня и единообразного resume; при LUKS `fileSystems."/".device` указывает на `/dev/mapper/<имя>`). |
| STO-4 | Swap — файл на отдельном томе без CoW, размер ≥ объёма RAM; создаётся средствами NixOS/disko либо `btrfs filesystem mkswapfile` (файл без CoW и сжатия; отдельная опция монтирования `nodatacow` не нужна и запрещена STO-1). Дополнительный сжатый swap в памяти — MAY. |
| STO-5 | **Гибернация — MUST для класса `laptop`**, SHOULD для остальных с автономным питанием. Задано устройство resume и смещение swap-файла (`my.host.resume.offset`, вычисляется после создания файла, пересчитывается при его пересоздании; `just hibernate-offset`). Драйвер дискретной GPU сохраняет состояние при сне. |
| STO-6 | Политика сна: закрытие крышки → сон с последующей гибернацией (задержка — параметр); критический заряд → гибернация; пункт Hibernate в меню питания работает; блокировка экрана срабатывает один раз. |
| STO-7 | **Эфемерный корень — опционально, по умолчанию выключен.** Если включается: только вместе с реальным откатом корня в initrd, постоянным томом с `neededForBoot`, единым списком persist; пользовательские данные постоянны. «Эфемерность» без отката корня — дефект. |
| STO-8 | Бэкапы: локальные снимки пользовательских данных + копия на внешний/удалённый носитель; проверка восстановления периодически; в бэкап обязательно ключи (SEC-13); хранилища моделей и кэши исключены. |
| STO-9 | Обслуживание: проверки целостности ФС по расписанию; GC по расписанию плюс ограничение числа поколений в загрузчике. |
| STO-10 | Secure Boot — **не включать по умолчанию**: есть сообщения о несовместимости с гибернацией (причина не установлена). Пробовать только после стабильной гибернации — с повторным прогоном теста. При повторной проверке сверять `cat /sys/kernel/security/lockdown`: на штатном ядре NixOS с Lanzaboote режим lockdown сам по себе не включается, поэтому не считать его причиной без измерения. |
| STO-11 | **Бюджет ёмкости.** Для каждого хоста в `docs/runbook.md` ведётся таблица: swap (≥ RAM), `/nix` с запасом на рост (замыкания CUDA/ML, нестабильный канал, поколения), библиотека игр, образы контейнеров, модели, срок хранения снимков. Библиотека игр, образы контейнеров и модели — на томах вне снимков (STO-1). Порог тревоги — свободного места < 15 %. Для малых накопителей (≤ 512 ГБ) бюджет утверждается до установки. |

**Приёмка гибернации:** три цикла hibernate/resume подряд; восстановились графическая сессия, оконные приложения, редактор, туннель; приложение на дискретной GPU работает после resume; в момент resume kill switch не открывает утечку.

## 11. Сеть и туннель

| ID | Правило |
|---|---|
| NET-1 | Слот `tunnel`: **один** модуль-владелец на реализацию; два модуля, определяющих один unit/файл, недопустимы. |
| NET-2 | Параметры подключения (адрес, идентификаторы, ключи, SNI) — только из sops (SEC-4). |
| NET-3 | Клиент проверяет подлинность сервера всеми доступными средствами протокола (включая постквантовые, если их использует сервер). |
| NET-4 | Локальный режим: слушает **только** loopback. |
| NET-5 | DNS: запросы приложений не уходят провайдеру напрямую, кроме доменов, которые политика направляет напрямую; политика IPv6 задана явно; клиент резолвит через собственный DNS-механизм туннеля. |
| NET-6 | Маршрутизация: частные сети → напрямую; трафик локальной юрисдикции по политике → напрямую; блокировка рекламы — опционально; остальное → туннель; явное catch-all-правило. |
| NET-7 | Режимы: **M1** — локальный прокси + переменные окружения (запасной; покрывает только процессы, читающие переменные, но не демоны); **M2** — прозрачный режим через виртуальный сетевой интерфейс (целевой; покрывает все приложения). В M2: маршрут к серверу туннеля исключён из туннеля (иначе петля); исходящий интерфейс клиента задаётся явно. |
| NET-8 | Kill switch (`killswitch`): в M2 с физического интерфейса разрешён только трафик loopback, локальной сети/DHCP, самого клиента туннеля (по cgroup/uid) и явно перечисленных служебных; остальное блокируется — в том числе в момент resume после гибернации. Блокировка — **отказом (reject)**, а не молчаливым отбрасыванием: клиент получает ошибку за секунды (иначе зависают приложения и не срабатывает fallback). |
| NET-9 | Сервис клиента: динамический пользователь, минимальные привилегии, credentials, песочница (защита системы и home, приватный tmp), автоперезапуск. |
| NET-10 | Переменные прокси для M1 — в одном месте (DOT-7). |
| NET-11 | Firewall: default deny; порты открывают фичи, которым они нужны; ручные диапазоны, дублирующие встроенные опции фич, запрещены. |
| NET-12 | Доступ к веб-интерфейсам сервисов, блокирующих адреса дата-центров, — через отдельный upstream на выходе (конкретизация — VPN_SUBSYSTEM, VPN-LLM-*); доступ по API-ключам от upstream не зависит и **не должен проходить через него**. |

**Приёмка:** внешний IP — из страны сервера туннеля без явной настройки приложения (M2); трафик по политике «напрямую» идёт напрямую; тесты утечек DNS/WebRTC/IPv6 чисты; скорость замерена относительно базовой; остановка сервиса блокирует внешний трафик.

## 18. Чек-листы

### 18.1 Добавить фичу
1. Определить домен и имя (FEAT-1); убедиться, что задача не покрыта существующей фичей (поиск).
2. Создать `modules/<домен>/<имя>.nix` с нужными классами (FEAT-2); параметры — из `my.*` (FEAT-3); имён пользователей, секретов и констант хоста нет.
3. Для приложения реестра — Nix даёт пакет/юнит, содержимое конфига — в dotfiles (DOT-3).
4. Включить в пресет или хост (FEAT-5, FEAT-8); добавить в каталог (раздел 6).
5. `nix fmt && nix flake check`, сборка затронутых хостов.

### 18.2 Добавить пакет
1. Пользовательский → `home.packages` фичи-владельца; системный → `environment.systemPackages` nixos-класса.
2. Пакет не стоит в другой фиче (ARCH-5). Тулчейн проекта — в проектное окружение (ARCH-9).
3. Из нестабильного канала — через overlay с комментарием-причиной.

### 18.3 Добавить хост / новое железо
1. Сгенерировать `machines/<имя>/hardware.nix`; при декларативной разметке — без описания файловых систем.
2. Скопировать `_template.nix` → `<имя>.nix`; заполнить `my.host.*` (класс, пользователи, `stateVersion`, GPU, диск, батарея, мониторы); выбрать пресеты.
3. Аппаратное — только составом `hardware/*` и `my.host` (HOST-3).
4. Создать ключ хоста, добавить recipient в `.sops.yaml`, обновить ключи файлов (SEC-7).
5. Для гибернации: после создания swap-файла вычислить `resume.offset` (STO-5).
6. Собрать хост; для headless — виртуальная машина.
7. Установка: образ установщика → разметка → доставка ключа хоста до первой активации (SEC-12) → установка из flake.

### 18.4 Добавить пользователя
1. Запись `modules/users/<имя>.nix`: `admin`, `capabilities`, режим dotfiles.
2. Добавить в `my.host.users` нужных хостов.
3. Создать ключ пользователя, добавить recipient, завести `secrets/users/<имя>.yaml`.
4. Если нужна новая capability — слово в словарь (USER-4) и пресеты.
5. Проверить изоляцию (USER-6) и сборку хоста.

### 18.5 Заменить реализацию слота
1. Создать фичу `<слот>-<новая>`; пакет/юнит/интеграция — внутри неё.
2. Создать каталог конфигурации в dotfiles, обновить `REGISTRY.md`; адаптерные файлы компонентов (SLOT-4d).
3. В пресете заменить реализацию; старую оставить или удалить (FEAT-8).
4. Контракты и остальные фичи не менялись — иначе ARCH-16 нарушен.

### 18.6 Добавить секрет
1. Класс A/B (SEC-2); значение — в `secrets/*.yaml` через sops.
2. Объявить в фиче-владельце; права 0400; доступ сервису через credentials.
3. Проверить: значения нет в `/nix/store` и в открытом виде в diff.

### 18.7 Изменить конфиг приложения
1. Правка в `~/.config/<app>/…` (симлинк на рабочую копию), коммит в dotfiles.
2. Хостозависимое значение — в `my.host` → машинный слой, не в dotfiles.
3. Ломающее изменение синтаксиса — тег и запись в `REGISTRY.md`; для воспроизводимой сборки — `nix flake update <dotfiles-input>`.

### 18.8 Перед коммитом
Форматирование, `nix flake check`, сканер секретов; нет секретов и приватных фактов; каталог и ADR обновлены; Conventional Commits.

### 18.9 Установка на чистую машину
Образ установщика → разметка → ключ хоста → установка из flake → первый вход (приложения реестра без конфигов) → `just dotfiles-clone` → приёмка (раздел 20).

## 19. Запрещено

1. Файлы-свалки и хосты с логикой (ARCH-4, ARCH-11).
2. Импорт фичи из фичи (ARCH-3); `import` как скрытый переключатель с побочными эффектами.

9. Эфемерный корень без отката (STO-7); Secure Boot без повторной проверки гибернации (STO-10).
10. Переменные прокси в нескольких местах (NET-10); локальный прокси не на loopback (NET-4).
11. Два форматтера Nix (DEV-8); два модуля, определяющих один unit/файл (NET-1).
12. Названия конкретных программ (кроме инструментов каркаса, ARCH-20), версий и пользователей в нормативной части (ARCH-16, ARCH-17, ARCH-18).
13. Временные обходы и «перенесём потом» (ARCH-19).

### A.6 Особенности реализации

**Hyprland + UWSM**
- `programs.hyprland` с UWSM; HM-модуль Hyprland не используется (DOT-3: конфиг композитора — dotfiles; интеграция с systemd — только UWSM, DESK-2).
- Префикс запуска приложений — `uwsm app --` (в машинном слое как переменная конфига), выход из сессии — `uwsm stop`.
- Переменные сессии — через env-файлы UWSM (`ПРОВЕРИТЬ`).
- Конфиг подключает машинный слой директивой `source`.
- Синтаксис правил окон/слоёв менялся между версиями, ведётся переход на Lua-конфиг — версионные заметки в `REGISTRY.md` (DOT-10).
- `AQ_DRM_DEVICES` — список через двоеточие: использовать udev-симлинки без двоеточий, а не пути `by-path` и не `cardN` (DESK-5).

**NVIDIA / гибридная графика**
- Открытые модули ядра (архитектура Turing поддерживается), modesetting, `powerManagement.enable` (нужен и для гибернации), PRIME offload + `nvidia-offload`.
- `powerManagement.finegrained` — включать после теста энергопотребления и гибернации.
- Steam: опция запуска `nvidia-offload %command%`.

**Компоненты оболочки**
- waybar: `include` + CSS `@import`; foot, mako, mpv — собственные `include` (`ПРОВЕРИТЬ` по версиям). Адаптеры рабочих столов Hyprland — отдельным файлом в `waybar/`.

**zsh / редактор**
- `ZDOTDIR` — через `programs.zsh.shellInit` (`/etc/zshenv`); HM `programs.zsh` не используется; интеграция direnv с zsh отключена, хук — в dotfiles.
- Пути к oh-my-zsh и плагинам — из машинного слоя с запасными путями дистрибутивов.
- Neovim нужной версии с новым API LSP; `lazy-lock.json` — в dotfiles.

**Туннель (Xray)**
- VLESS + Reality, `flow = xtls-rprx-vision`, проверка постквантовой подписи на клиенте обязательна; клиенты на sing-box её не поддерживали — использовать оригинальный `xray-core`.
- Нативный TUN-inbound есть в новых версиях xray-core; проверить версию пакета в релизе, иначе — из нестабильного канала. Явно задать `autoOutboundsInterface`, исключить маршрут к серверу из туннеля, сервису — `CAP_NET_ADMIN`.
- DNS: `.ru` и `geosite:category-ru` → российский резолвер напрямую; остальное → DoH через прокси; стратегия IPv4, пока IPv6 не проверен.
- Маршрутизация: private → direct; `geosite:category-ru` и `geoip:ru` → direct; `geosite:category-ads-all` → block; остальное → proxy.
- `XRAY_LOCATION_ASSET` вручную **не задавать** (обёртка пакета делает сама).
- Конфиг рендерится из sops-шаблона; в Nix только структура маршрутизации.
- Upstream для веб-интерфейсов LLM реализуется подсистемой VPN (VPN-LLM-*): явные `domain:`-записи на выходе; гео-теги — только после проверки наличия в данных выхода; API-хосты провайдеров направляются в обход upstream.

**Игры, ML, контейнеры**
- Steam: `programs.steam` + `extraCompatPackages`; `openFirewall` — только нужные флаги.
- Ollama: `services.ollama` с CUDA; имена опций — `ПРОВЕРИТЬ`; модели в `/var/lib/ollama`.
- Docker: членство в группе `docker` равнозначно правам root (DEV-6).

## 0. Назначение и обозначения

**0.1 Что это.** Последовательность шагов от пустого репозитория до принятой системы по критериям A1–A18 (Архитектура), VPN-A1…A15, AI-A1…A14 и проверкам структуры C1…C11. Путь на этом и на каждом следующем хосте — **чистая установка**: диск размечается заново, система ставится из flake; данные пользователя возвращаются из проверенного бэкапа. Шаги относятся к любому хосту, который так устанавливается, — ноутбуку сейчас, личному ноутбуку и персональному компьютеру (с несколькими пользователями) позже.

**0.2 Обозначения.**

| Обозначение | Смысл |
|---|---|
| `R<этап>.<n>` | Идентификатор шага (например, `R4.7`) |
| **G<n>** | Gate — условия выхода из этапа; следующий этап начинается только после Gate |
| **PNR-<n>** | Точка невозврата (3.3): действие, которое нельзя откатить штатно |
| `☐` | Колонка «Готово»: отмечайте по мере выполнения; это и есть трекер |
| ПРОВЕРИТЬ | Как в Архитектуре: не подтверждено, дана проверка |

**0.3 Для LLM-ассистента.** Предлагая работу, называйте ID шага и критерий готовности из таблицы. Не предлагайте шаг следующего этапа, пока не выполнен Gate предыдущего. Любое действие, связанное с PNR, — только после явного подтверждения владельца.

**0.4 Оценки.** Часы — для одного человека, ориентир ±30 %. Суммарно ≈ 100–175 ч, при 8–10 ч в неделю — **3–5 месяцев**. Оценки не обязательства: при перерасходе пересматривайте объём этапов 6–8, а не качество Gate'ов этапов 0–5.

## 1. Исходные условия

### 1.1 Что строим

Ноутбук ASUS TUF Gaming F15 (laptop_spec: Core i5-10300H, GTX 1650 с 4 ГБ VRAM, 24 ГБ RAM асимметрично, NVMe 512 ГБ, гибридная графика **без MUX**). Один пользователь `sgm`, один хост `sgms-laptop`, capabilities `desktop development office media gaming ml containers`. Результат — система, описанная пятью документами.

### 1.2 Что нужно иметь под рукой на старой машине

На каждой машине, которую переводите на эту конфигурацию: рабочая копия старого (прежнего для этой машины) репозитория dotfiles/конфигов — локально, приватно; она источник для переноса конфигов (R4.1). Если на машине уже есть пользователь, желаемые uid/gid стоит зафиксировать и задать явно (R2.2) — тогда данные, восстановленные из бэкапа, не потребуют `chown`.

### 1.3 Ограничения среды

- Внешняя сеть нестабильна без туннеля: загрузка с зарубежных CDN может зависать (VPN_SUBSYSTEM 3.2). Поэтому **до первой установки** нужен временный путь в сеть (R0.8).
- Старый репозиторий публичен и содержит значения, ставшие скомпрометированными; они заменяются **до** любых других работ (R0.9, VPN-SEC-3).
- NVMe всего 512 ГБ. Бюджет места — предмет контроля на каждом Gate (STO-11).

### 2.2 Зависимости и критический путь

```
0 ─▶ 1 ─▶ 2 ─▶ 3 ─▶ 4 ─▶ 5 ─▶ 6 ─┬─▶ 8 ─▶ 9
                                          └─▶ 7 ─┘
```

Критический путь: 0 → 1 → 2 → 3 → 4 → 5 → 6 → 8 → 9. Ключевые зависимости:

- Облачные роли AI (R8.4) требуют режима M2 и kill switch (этап 5).
- Агенты (R8.5) требуют шаблонов и `env-manager` (этап 6).
- Приёмка AI-A4 («игра и инференс») требует игрового оптимизатора (этап 7).
- Приёмка kill switch и M2 требует гибернации (R5.1 раньше R5.4).
- Приёмка прокси-переменных в GUI (VPN-A4) требует рабочего стола (этап 4).

**Параллельные дорожки** (не блокируют критический путь):

| Дорожка | Когда начать | Когда нужна |
|---|---|---|
| Выбор и оплата второго выхода (VPN-RES-1) | R0.10 | R5.6 |
| Перенос конфигов приложений в dotfiles | R4.1 | этап 4 |
| Документация и ADR | R1.6 | Каждый Gate |

### 2.3 Gate'ы и точки невозврата

| Точка | Событие | Обратимость |
|---|---|---|
| **PNR-1** | Ротация ключей выхода (R0.9): старые значения перестают приниматься | Необратима по замыслу; последствие — старый клиент не работает, пока не обновлён (R0.8) |
| **PNR-2** | Стирание диска (R2.8) | После этого — только возврат из бэкапа |
| **PNR-3** | Удаление старых поколений, старого репозитория, бэкапов (R9.10) | Необратима. Только после G9 и 14 дней спокойной эксплуатации |

## 3. Правила проведения работ

| № | Правило |
|---|---|
| W1 | **Одна рабочая сессия — один зелёный `just check`** и система в загружаемом состоянии. Не заканчивайте сессию на полпути в ветке `main` |
| W2 | Ветки `stage/<n>-<тема>` → `main` через CI; `main` всегда собирается (OPS-6). Каждый Gate получает тег `g<n>` в `nixos-config` и dotfiles |
| W3 | Применение на реальной машине — только по OPS-3: `build` → `nvd diff` → `test` → `boot` → перезагрузка. Прямой `switch` без `test` — запрещён до G9 |
| W4 | После каждого Gate — снимок подтомов (R0.4) и запись в журнал: что принято, какие критерии, дата |
| W5 | Сборка мусора: до PNR-3 поколения не удаляются |
| W6 | Сначала правило, потом исключение: если приходится нарушать Архитектуру, оформляется ADR (OPS-7), а не «временное решение» (ARCH-19). Исключение — временный bootstrap-путь в сеть (R0.8), у которого есть срок удаления |
| W7 | Каждая новая фича: каталог (FEAT-7), пресет (FEAT-8), `just check`, затем сборка хоста |
| W8 | Секреты не вводятся в терминал на публичных каналах и не копируются из чата (SEC-5); значения — только через `sops-edit` |
| W9 | Runbook держится **офлайн** (телефон/бумага): аварийные процедуры должны быть доступны без работающей сети и графики |

# Приложения

## Приложение A. Бэкап и проверка (R0.4)

Принцип: **два независимых слоя** — снимки на самом диске (от ошибок конфигурации) и внешняя копия (от потери диска). Копия считается существующей только после проверки восстановления.

```sh
# Верхний уровень Btrfs, чтобы снимки лежали вне смонтированных подтомов
sudo mkdir -p /mnt/top && sudo mount -o subvolid=5 /dev/disk/by-uuid/<uuid-btrfs> /mnt/top
D=$(date +%F)
sudo btrfs subvolume snapshot -r /mnt/top/@home    /mnt/top/@snap-home-$D
sudo btrfs subvolume snapshot -r /mnt/top/@        /mnt/top/@snap-root-$D
sudo btrfs subvolume snapshot -r /mnt/top/@persist /mnt/top/@snap-persist-$D   # если есть

# Внешняя копия на отдельный Btrfs-носитель
sudo btrfs send /mnt/top/@snap-home-$D | sudo btrfs receive /mnt/backup/
sudo rsync -aHAX /boot/ /mnt/backup/esp-$D/                                   # ESP
sudo rsync -aHAX /etc/ssh/ /mnt/backup/etc-ssh-$D/                            # ключи хоста

# Проверка: сравнение содержимого и пробное восстановление образца
sudo rsync -rcn --delete /mnt/top/@snap-home-$D/ /mnt/backup/@snap-home-$D/ | head
```

Если внешний носитель не Btrfs, используйте `rsync -aHAX` либо резервное копирование с шифрованием; пробное восстановление обязательно в любом случае. Ключи (age, SSH) хранятся **отдельно** от диска (SEC-13).

## 0. Назначение и обозначения

**0.1 Что это.** Последовательность шагов от пустого репозитория до принятой системы по критериям A1–A18 (Архитектура), VPN-A1…A15, AI-A1…A14 и проверкам структуры C1…C11. План допускает два способа получить систему на ноутбуке:

| Трек | Суть | Что с данными |
|---|---|---|
| **[C]** Чистая установка | Диск размечается заново, система ставится из flake | Всё стирается; данные пользователя возвращаются из проверенного бэкапа (если они есть) |
| **[M]** Миграция на месте | Существующая файловая система не пересоздаётся; старая система переключается на новую конфигурацию | **Файловая система, файлы и папки пользователя сохраняются как есть** |

Шаг помечен треком: `C`, `M` или `C+M`. Шаги без пометки общие.

**0.2 Обозначения.**

| Обозначение | Смысл |
|---|---|
| `R<этап>.<n>` | Идентификатор шага (например, `R4.7`) |
| **G<n>** | Gate — условия выхода из этапа; следующий этап начинается только после Gate |
| **PNR-<n>** | Точка невозврата (3.3): действие, которое нельзя откатить штатно |
| **PoS** | Point of Switch — первое переключение реальной машины на новую конфигурацию (только трек M, R4.7) |
| `☐` | Колонка «Готово»: отмечайте по мере выполнения; это и есть трекер |
| ПРОВЕРИТЬ | Как в Архитектуре: не подтверждено, дана проверка |

**0.3 Для LLM-ассистента.** Предлагая работу, называйте ID шага, трек и критерий готовности из таблицы. Не предлагайте шаг следующего этапа, пока не выполнен Gate предыдущего. Любое действие, связанное с PNR, — только после явного подтверждения владельца.

**0.4 Оценки.** Часы — для одного человека, ориентир ±30 %. Суммарно ≈ 100–175 ч, при 8–10 ч в неделю — **3–5 месяцев**. Оценки не обязательства: при перерасходе пересматривайте объём этапов 6–8, а не качество Gate'ов этапов 0–5.

## 1. Исходные условия

### 1.1 Что строим

Ноутбук ASUS TUF Gaming F15 (laptop_spec: Core i5-10300H, GTX 1650 с 4 ГБ VRAM, 24 ГБ RAM асимметрично, NVMe 512 ГБ, гибридная графика **без MUX**). Один пользователь `sgm`, один хост `sgms-laptop`, capabilities `desktop development office media gaming ml containers`. Результат — система, описанная пятью документами.

### 1.2 Допущения о старой системе (трек M)

Это допущения. Шаг R0.2 проверяет каждое; если допущение неверно, действуйте по третьему столбцу.

| № | Допущение | Если не так |
|---|---|---|
| H1 | Старая система — NixOS на стабильном канале **того же релиза** (26.05) | Сначала штатно обновите старую систему до 26.05 **отдельной операцией** и проживите на ней неделю; смену релиза не совмещают с миграцией |
| H2 | Одна Btrfs с подтомами `@`, `@home`, `@nix`, `@persist`, `@swap`; ESP на FAT; swap-файл в `@swap`; шифрования нет | Составьте таблицу фактической раскладки (Приложение A) и подстройте R2.5 и R5.1; не пересоздавайте ничего |
| H3 | Есть слой `/persist` с привязками (impermanence) | Если его нет, шаг R2.6 пропускается |
| H4 | Пользователь `sgm`, uid 1000; данные пользователя лежат в `@home` | Зафиксируйте фактический uid и gid и задайте их явно (R2.2) |
| H5 | Загрузчик systemd-boot, ESP со свободным местом ≥ 200 МБ | Уменьшите лимит поколений или освободите место; расширять ESP на месте — только по отдельному решению |
| H6 | Поколения старой системы **не удалены** (GC выключен или есть запас) | Откат на старое поколение будет невозможен; тогда единственный откат — снимки и бэкап, а PoS откладывается до их проверки |
| H7 | Рабочая копия старого репозитория лежит локально | Нужна для переноса конфигов (R4.1); клонируйте приватно |

### 1.3 Ограничения среды

- Внешняя сеть нестабильна без туннеля: загрузка с зарубежных CDN может зависать (VPN_SUBSYSTEM 3.2). Поэтому **до первой установки** нужен временный путь в сеть (R0.8).
- Старый репозиторий публичен и содержит значения, ставшие скомпрометированными; они заменяются **до** любых других работ (R0.9, VPN-SEC-3).
- NVMe всего 512 ГБ. Бюджет места — предмет контроля на каждом Gate (STO-11).

### 1.4 Что не меняется при миграции (инварианты трека M)

Нарушение любого пункта — основание остановить работы и откатиться.

| Инвариант | Как контролируется |
|---|---|
| Таблица разделов и файловая система (UUID Btrfs и ESP) | `lsblk -f` до и после PoS идентичны |
| Содержимое `@home`: файлы и папки пользователя | R4.7: сравнение списков файлов со снимком (Приложение C) |
| uid и gid пользователя; uid-карты системных пользователей | `/var/lib/nixos` перенесён до PoS (R2.6) |
| `system.stateVersion` и версия состояния Home Manager | Значение берётся из **старой** конфигурации (R2.2); не равно версии канала (HOST-5) |
| Ключи SSH хоста и `machine-id` | Остаются на месте (R2.6) |
| Старые поколения системы | GC заморожен до PNR-3 (R0.3) |

## 2. Выбор трека и устройство миграции

### 2.1 Что выбрать

| Ситуация | Трек |
|---|---|
| Эта машина, данные нужно сохранить как есть | **M** (по умолчанию) |
| Новый диск или новая машина; серверный выход на VPS (VPN S8) | **C** |
| Эта машина, но нужно шифрование диска сразу (STO-2) | **C**: бэкап → чистая установка → возврат данных. Альтернатива для M — шифрование «на месте» (R5.5), рискованнее |
| Сомнения | **M** с PoS в конце этапа 4: до PoS ничего необратимого не происходит |

### 2.2 Как устроена миграция на месте

1. Новая конфигурация разрабатывается **рядом** со старой системой, в отдельном репозитории с чистой историей (этапы 1–4). Старая система остаётся рабочей.
2. Проверка до переключения: сборка хоста без активации, сравнение замыканий, виртуальная машина, предполётная проверка отрисованного конфига туннеля.
3. **PoS** — одно переключение: `nixos-rebuild test` (откат перезагрузкой), затем `boot`. Старое поколение остаётся в меню загрузчика.
4. Подтомы Btrfs не пересоздаются; недостающие создаются **онлайн** уже после PoS (R5.1).
5. Перед PoS делаются снимки подтомов и бэкап; они защищают то, что откатом поколения не откатывается (состояние сервисов, данные).

| Вариант миграции | Плюсы | Минусы | Решение |
|---|---|---|---|
| **A. На месте** (поколение + снимки) | Состояние хоста сохраняется само; просто; откат поколением | Состояние, изменённое новой системой, откатывается только снимком | **Выбран** |
| B. Новый корневой подтом рядом | Откат и конфигурации, и состояния корня | Всё состояние (`/etc`, `/var`) переносится вручную; больше шагов | Запасной, если H6 не выполнено |
| C. Переустановка и восстановление | Чистейший результат | Нарушает требование сохранить ФС | Это трек C |

### 2.3 Чем различаются треки по этапам

| Этап | [C] | [M] |
|---|---|---|
| 0 | Бэкап нужен для возврата данных | Бэкап и снимки — страховка; плюс инвентаризация и заморозка GC |
| 2 | Разметка (disko) и установка | Режим `adopt`: файловые системы не трогаются; переносится состояние из `/persist`; **активации нет** |
| 3 | Включаются на живой системе | Проверяются до PoS: предполётный запуск рядом со старым клиентом |
| 4 | Загрузка в готовую систему | **PoS** в конце этапа |
| 5 | Подтомы уже созданы разметкой | Подтомы добавляются онлайн; swap проверяется и при нужде пересоздаётся |
| 9 | Очистка загрузочных остатков | PNR-3: удаление старых поколений, `/persist`, старого репозитория |

Этапы 1, 6, 7, 8 одинаковы.

### 3.2 Зависимости и критический путь

```
0 ─▶ 1 ─▶ 2 ─▶ 3 ─▶ 4 ══PoS══▶ 5 ─▶ 6 ─┬─▶ 8 ─▶ 9
                                          └─▶ 7 ─┘
```

Критический путь: 0 → 1 → 2 → 3 → 4 → 5 → 6 → 8 → 9. Ключевые зависимости:

- Облачные роли AI (R8.4) требуют режима M2 и kill switch (этап 5).
- Агенты (R8.5) требуют шаблонов и `env-manager` (этап 6).
- Приёмка AI-A4 («игра и инференс») требует игрового оптимизатора (этап 7).
- Приёмка kill switch и M2 требует гибернации (R5.2 раньше R5.6).
- Приёмка прокси-переменных в GUI (VPN-A4) требует рабочего стола (этап 4).

**Параллельные дорожки** (не блокируют критический путь):

| Дорожка | Когда начать | Когда нужна |
|---|---|---|
| Выбор и оплата второго выхода (VPN-RES-1) | R0.10 | R5.8 |
| Перенос конфигов приложений в dotfiles | R4.1 | R4.7 |
| Документация и ADR | R1.6 | Каждый Gate |

### 3.3 Gate'ы и точки невозврата

| Точка | Событие | Обратимость |
|---|---|---|
| **PNR-1** | Ротация ключей выхода (R0.9): старые значения перестают приниматься | Необратима по замыслу; последствие — старый клиент не работает, пока не обновлён (R0.8) |
| **PNR-2** | [C] стирание диска (R2.9) | После этого — только возврат из бэкапа |
| **PoS** | [M] `boot` новой конфигурации (R4.7) | Обратима: старое поколение в меню загрузчика; состояние — из снимков |
| **PNR-3** | Удаление старых поколений, старого репозитория, `/persist`, бэкапов (R9.7) | Необратима. Только после G9 и 14 дней спокойной эксплуатации |
| **PNR-4** | [M, опц.] шифрование на месте (R5.5) | Рискованна: прерывание грозит потерей данных. Только при проверенном бэкапе |

## 4. Правила проведения работ

| № | Правило |
|---|---|
| W1 | **Одна рабочая сессия — один зелёный `just check`** и система в загружаемом состоянии. Не заканчивайте сессию на полпути в ветке `main` |
| W2 | Ветки `stage/<n>-<тема>` → `main` через CI; `main` всегда собирается (OPS-6). Каждый Gate получает тег `g<n>` в `nixos-config` и dotfiles |
| W3 | Применение на реальной машине — только по OPS-3: `build` → `nvd diff` → `test` → `boot` → перезагрузка. Прямой `switch` без `test` — запрещён до G9 |
| W4 | После каждого Gate — снимок подтомов (R0.4) и запись в журнал: что принято, какие критерии, дата |
| W5 | Сборка мусора: до PNR-3 поколения не удаляются; старые автоматические очистки отключены (R0.3) |
| W6 | Сначала правило, потом исключение: если приходится нарушать Архитектуру, оформляется ADR (OPS-7), а не «временное решение» (ARCH-19). Исключение — временный bootstrap-путь в сеть (R0.8), у которого есть срок удаления |
| W7 | Каждая новая фича: каталог (FEAT-7), пресет (FEAT-8), `just check`, затем сборка хоста |
| W8 | Секреты не вводятся в терминал на публичных каналах и не копируются из чата (SEC-5); значения — только через `sops-edit` |
| W9 | Runbook держится **офлайн** (телефон/бумага): аварийные процедуры должны быть доступны без работающей сети и графики |

## Приложение B. Бэкап и проверка (R0.4)

Принцип: **два независимых слоя** — снимки на самом диске (от ошибок конфигурации) и внешняя копия (от потери диска). Копия считается существующей только после проверки восстановления.

```sh
# Верхний уровень Btrfs, чтобы снимки лежали вне смонтированных подтомов
sudo mkdir -p /mnt/top && sudo mount -o subvolid=5 /dev/disk/by-uuid/<uuid-btrfs> /mnt/top
D=$(date +%F)
sudo btrfs subvolume snapshot -r /mnt/top/@home    /mnt/top/@snap-home-$D
sudo btrfs subvolume snapshot -r /mnt/top/@        /mnt/top/@snap-root-$D
sudo btrfs subvolume snapshot -r /mnt/top/@persist /mnt/top/@snap-persist-$D   # если есть

# Внешняя копия на отдельный Btrfs-носитель
sudo btrfs send /mnt/top/@snap-home-$D | sudo btrfs receive /mnt/backup/
sudo rsync -aHAX /boot/ /mnt/backup/esp-$D/                                   # ESP
sudo rsync -aHAX /etc/ssh/ /mnt/backup/etc-ssh-$D/                            # ключи хоста

# Проверка: сравнение содержимого и пробное восстановление образца
sudo rsync -rcn --delete /mnt/top/@snap-home-$D/ /mnt/backup/@snap-home-$D/ | head
```

Если внешний носитель не Btrfs, используйте `rsync -aHAX` либо резервное копирование с шифрованием; пробное восстановление обязательно в любом случае. Ключи (age, SSH) хранятся **отдельно** от диска (SEC-13).

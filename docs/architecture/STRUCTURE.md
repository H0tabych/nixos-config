# Структура репозитория NixOS-конфигурации

> Версия 1.1 · 2026-10-09 · Статус: действующий (изменения 1.1: в корень добавлены `CLAUDE.md` и `.claude/`, в `docs/architecture/` — `ROADMAP.md`; раздел 2, 6, ADR-31, Приложение E)
> **Подчинено** «Архитектуре NixOS-систем» v2.1 (разделы 2–6, 8, 16) и конкретизирует её раздел 4. При расхождении приоритет у Архитектуры; расхождения, которые документ вносит сознательно, собраны в разделе 13 и оформляются записями ADR-31 и ADR-32.
> **Разделы 0–13** не называют конкретных программ, версий и пользователей (ARCH-16…18), кроме инструментов каркаса (ARCH-20). **Приложение E** — эталонное дерево для текущей системы (Приложение A Архитектуры). **Приложение M** — матрица соответствия требованиям Архитектуры, AI_SUBSYSTEM и VPN_SUBSYSTEM.
> Секретов и приватных фактов нет (SEC-5). Имена в примерах — плейсхолдеры, кроме Приложения E.

## 0. Назначение и как пользоваться

**0.1 Что решает документ.** Отвечает на три вопроса, один раз и проверяемо: *где что лежит*, *почему именно там*, *как это менять*. Охватывает два репозитория: основной (`nixos-config`) и отдельный `dotfiles` (раздел 7).

**0.2 Мера качества.** Структура считается хорошей, если выполняются семь критериев. Каждое решение раздела 1 привязано к одному или нескольким из них.

| № | Критерий | Как проверяется |
|---|---|---|
| K1 | **Предсказуемость.** По названию задачи путь к файлу угадывается без поиска | Раздел 9: порядок вопросов даёт единственный ответ |
| K2 | **Локальность изменений.** Типовое изменение затрагивает ≤ 3 существующих файла | Раздел 10: таблица «сценарий → файлы» |
| K3 | **Проверяемость.** Нарушение структуры находит CI, а не ревью | Раздел 8: проверки C1…C12 |
| K4 | **Малая единица.** Файл ≲ 150 строк, каталог ≤ 15 фич (ARCH-12) | STR-5, проверка C6 |
| K5 | **Один факт — одно место** (ARCH-5) | Нет каталогов-свалок (STR-3), уникальные имена (STR-4) |
| K6 | **Переносимость.** Данные, конфиги и железо отделены от логики | Разделы 4, 7; STR-10 |
| K7 | **Безопасность публичного репозитория** | Закрытый список корня (STR-1), `secrets/` (раздел 4), CI C9 |

**0.3 Для LLM-ассистента.** Предлагая новый файл, всегда указывайте: путь по разделу 9, класс (`nixos` / `homeManager`), владельца (фича или пресет), пресет, в который файл включается, и набор затрагиваемых файлов (раздел 10). Правила имеют ID `STR-n`; ссылайтесь на них. Если запрос требует нарушить правило, скажите об этом и предложите вариант в рамках правил либо запись ADR.

## 1. Принятые решения

| № | Решение | Критерии | Альтернативы (раздел 11) |
|---|---|---|---|
| D1 | **Путь = адрес.** `modules/<домен>/<фича>.nix`, ровно два уровня; имя файла = имя фичи | K1, K5 | Плоский список; глубокие деревья |
| D2 | **Домен отвечает «что это», пресет — «кому и когда».** Каталоги группируют по назначению, состав для пользователя и хоста задаётся только в `presets/` и `hosts/` | K1, K2 | Группировка по capability |
| D3 | **Слоты соседствуют.** `bar-<р1>.nix` и `bar-<р2>.nix` лежат рядом; замена реализации — новый файл рядом + строка в пресете | K2 | Подкаталог на слот |
| D4 | **Хост — такой же модуль, как остальные**, и лежит в `modules/hosts/`; нет второго дерева `hosts/` с другим механизмом импорта | K1, K5 | Отдельное дерево хостов |
| D5 | **Данные отделены от логики.** Пользователи, хосты, железо, секреты — каталоги данных; логики в них нет | K2, K6 | Данные внутри фич |
| D6 | **Не-Nix-модуль не лежит среди модулей.** Он либо вне `modules/`, либо имеет префикс `_` и принадлежит одной фиче | K3, K5 | Смешанные каталоги |
| D7 | **Конфиги приложений — в отдельном репозитории dotfiles** (ARCH-15). В `nixos-config` их нет | K6 | Монорепозиторий |
| D8 | **Структура проверяется машиной.** Каждое правило STR либо проверяется в CI, либо помечено как ревью | K3 | Только соглашения |
| D9 | **Нет свалок.** Нет `lib/`, `overlays/`, `pkgs/`, `common/`, `misc/`, `utils/` (ARCH-11) | K5 | Каталоги общих файлов |
| D10 | **Документация и решения в репозитории**, в `docs/`; ADR — по одному файлу на решение | K1, K3 | Внешняя вики |

## 2. Корень репозитория

**STR-1.** Корень содержит **только** перечисленное ниже. Новый элемент корня — запись ADR.

```
nixos-config/
├── flake.nix              # inputs + mkFlake; логики нет
├── flake.lock             # в git; обновление осознанное (OPS-3)
├── justfile               # единая точка входа для людей и CI
├── README.md              # ≤ 60 строк: что это, ссылка на docs/README.md
├── .envrc                 # use flake — оболочка разработки репозитория
├── .editorconfig
├── .gitignore             # result*, .env*, ключи age, /docs/private/ (SEC-6)
├── .gitleaks.toml         # правила сканера секретов (SEC-9, VPN-SEC-8)
├── .sops.yaml             # только публичные recipients (SEC-7)
├── CLAUDE.md              # инструкции ассистента: ≤ 200 строк, ссылки на правила по ID (раздел 2)
├── .claude/               # общие настройки ассистента: settings.json, rules/, commands/ (раздел 2)
├── .github/workflows/     # CI (раздел 5.3)
├── modules/               # ТОЛЬКО flake-parts-модули (раздел 3)
├── machines/              # сгенерированное железо хостов (раздел 3.7)
├── secrets/               # sops-файлы (раздел 4.1)
├── assets/                # бинарные ресурсы Nix-владеемых компонентов (раздел 4.2)
├── templates/             # шаблоны проектов (раздел 4.3)
├── tests/                 # проверки поведения (раздел 5.1)
├── scripts/               # скрипты для just/CI/хуков (раздел 5.2)
└── docs/                  # документация и ADR (раздел 6)
```

| Элемент | Правило |
|---|---|
| `flake.nix` | Описывает `inputs` и одну строку `mkFlake … (import-tree ./modules)`. Любая логика — в `modules/core/`. Каждый input, кроме `nixpkgs`, `nixpkgs-unstable` и самих flake-parts/import-tree, имеет `follows` (ARCH-14, A16) |
| `justfile` | Рецепты — только оболочки над `nix`, `sops`, `nvd`, `scripts/*`. Бизнес-логики нет. Список рецептов — 5.4 |
| `README.md` | Не дублирует `docs/`; факт живёт в одном месте (ARCH-5) |
| `.gitignore` | Содержит `/docs/private/`, хотя приватные материалы хранятся **вне** репозитория: это страховка от случайного `git add`. Также `CLAUDE.local.md` и `.claude/settings.local.json` (личные настройки), `.direnv/`, `result*`, `.env*`, файлы ключей |
| `CLAUDE.md` | Не дублирует документы: только цель, карта документов с правилами поиска по ID, жёсткие запреты, протокол работы и строка «текущее состояние». Размер ≤ 200 строк (крупнее — теряется точность следования). Большие документы через `@`-импорт **не подключаются**: импорт загружается при запуске и не уменьшает расход контекста |
| `.claude/` | `settings.json` — права (запрет необратимых команд и чтения секретов, разрешение проверок); `rules/*.md` — правила с `paths:` (подключаются только при работе с подходящими файлами); `commands/*.md` — повторяющиеся процедуры. Личное — только в `settings.local.json` (в `.gitignore`). Секретов нет. Имя и формат задаёт сам инструмент: к ARCH-16/ARCH-18 не относится |

Чего в корне **нет и не будет**: `hosts/`, `home-manager/`, `lib/`, `overlays/`, `pkgs/`, `common/`, `private/`, `result*`, файлов с ключами и значениями секретов.

## 3. `modules/`: устройство

### 3.1 Виды каталогов и домены

**STR-2.** Каждый `.nix` в `modules/`, не начинающийся с `_`, — flake-parts-модуль (ARCH-2). Глубина — **ровно два уровня**: `modules/<домен>/<файл>.nix`. Исключения: `hosts/` и `users/` — каталоги данных, в них допустимы подкаталоги-группы при росте (раздел 12); `_`-пути не считаются.

**STR-3.** Набор доменов — **закрытый** (таблица). Новый домен — запись каталога Архитектуры (FEAT-7) и ADR. Каталогов-свалок нет (ARCH-11).

Четыре вида каталогов, и вид определяет, что в нём допустимо:

| Вид | Домены | Что внутри | Чего нет |
|---|---|---|---|
| **Каркас** | `core` | Модули самого flake: опции, форматтер, проверки, оболочка разработки | Фич с конфигурацией системы |
| **Фичи** | `base` `hardware` `storage` `security` `network` `desktop` `shell` `dev` `office` `media` `gaming` `ai` | По одной фиче на файл (ARCH-1) | Составов, данных пользователей и хостов |
| **Составы** | `presets` `hosts` | Только `imports` и значения `my.host.*` (FEAT-5, ARCH-4) | Пакетов, сервисов, логики |
| **Данные** | `users` | Записи `my.users.<имя>` (ARCH-17) | Логики, секретов |

| Домен | Критерий принадлежности («это про…») | Примеры файлов |
|---|---|---|
| `core` | сам репозиторий, не система | `options`, `lib`, `treefmt`, `checks-*` |
| `base` | то, без чего не работает ни один хост | `nix-settings`, `locale-keyboard`, `users`, `hm`, `fonts`, `host-facts` |
| `hardware` | физические устройства и их питание | `gpu-*`, `power`, `sleep`, `audio`, `bluetooth` |
| `storage` | диск, swap, снимки, бэкап | `layout`, `swap`, `maintenance`, `backup` |
| `security` | защита и секреты | `sops`, `ssh`, `hardening`, `firewall` |
| `network` | сеть, DNS, туннель, kill switch | `network-manager`, `tunnel-*`, `killswitch` |
| `desktop` | графическая сессия и её компоненты | `session-*`, `bar-*`, `theme` |
| `shell` | командная строка пользователя | `shell-*`, `vcs-tools`, `terminal-*`, `dotfiles-link` |
| `dev` | инструменты разработки | `editor-*`, `lsp-global`, `containers-*`, `databases` |
| `office` `media` `gaming` | прикладные домены (capability с тем же именем) | `office-suite-*`, `video-player-*`, `game-platform-*` |
| `ai` | ML и агенты | `ai-facts`, `inference-service-*`, `llm-gateway` |

**Правило выбора домена.** Файл кладётся по тому, **что он есть**, а не по тому, **кто им пользуется**. Менеджер уведомлений — `desktop`, даже если нужен только игровому пользователю; кто его получит — решает пресет.

### 3.2 Именование

**STR-4.** Имена в `modules/` подчиняются таблице.

| Объект | Правило | Пример (плейсхолдеры) |
|---|---|---|
| Файл фичи | `kebab-case.nix`; **имя файла = имя фичи** (FEAT-1) = ключ `flake.modules.<класс>.<имя>` | `notifier-xyz.nix` |
| Реализация слота | `<слот>-<реализация>`; слот — роль из каталога; `<р>` — **основная программа**, сопутствующие утилиты живут внутри файла | `bar-xyz.nix`, `screenshot-xyz.nix` |
| Набор без слота | Без суффикса; признак — замена одной программы другой не имеет смысла (в наборе несколько равноправных программ) | `databases.nix`, `vcs-tools.nix`, `lsp-global.nix`, `fonts.nix`, `theme.nix` |
| Фича-факты | `<подсистема>-facts`: только объявления опций `my.*`, без логики (ARCH-4) | `host-facts.nix`, `ai-facts.nix`, `tunnel-facts.nix` |
| Приватная часть | `_<владелец>-<часть>.<ext>` рядом с владельцем (3.4) | `_tunnel-policy.nix` |
| Пресет | Имя класса хоста или capability, без суффикса; **файл = пресет** | `desktop.nix`, `laptop.nix` |
| Хост | `<имя-хоста>.nix`; имя — уникальное, не совпадающее с именем фичи или пресета; рекомендуемый вид `<владелец-или-роль>-<класс>` | `alice-laptop.nix` |
| Пользователь | `<имя>.nix`; имя публично (SEC-2, USER-7) | `alice.nix` |

**STR-4a. Глобальная уникальность имён файлов.** Пространство `flake.modules.<класс>.*` плоское: два файла с одним именем молча сольются в один модуль и нарушат ARCH-1. Поэтому **имя файла (без `_`-путей) уникально во всём `modules/`**; это проверяется (C2). Следствия:

- **Имена пресетов зарезервированы**: `base laptop workstation server vm user-base desktop development office media gaming ml containers tunnel` нельзя дать ни хосту, ни фиче. Хост, выполняющий роль сервера, называется по роли (`exit-…`), а не `server`.
- **Фича, реализующая capability, не носит имя capability.** Capability `containers` — это пресет `presets/containers.nix`; рантайм — фича `containers-<р>`. Так ключ `flake.modules.homeManager.containers`, который требует USER-3, определён ровно один раз.
- **`default.nix` в `modules/` запрещён**: import-tree подключит его как обычную фичу, а имя повторится.

**STR-4b.** Суффиксы `-<р>` у слотов определяются Приложением A Архитектуры (таблица A.3): всё, что там перечислено как «слот → реализация», имеет суффикс. Это снимает неоднозначность каталога раздела 6, где часть слотов записана без `<р>` (`office-suite`, `video-player`, `containers`, `env-manager`, …).

### 3.3 Анатомия файла фичи

**STR-5.** Файл фичи начинается с заголовка из одной строки метаданных и коротких комментариев; затем — модуль.

```nix
# Фича: notifier-xyz · Слот: notifier · Домен: desktop · Классы: H · Для: пользователей с capability desktop
# Контракт: SLOT-4. Содержимое конфига — dotfiles/xyz (DOT-3); здесь только пакет и юнит.
# Зависимости: по составу пресета; жёсткие — через assertions (ниже).
{ ... }: {
  flake.modules.homeManager.notifier-xyz = { pkgs, ... }: {
    home.packages = [ pkgs.xyz ];
    systemd.user.services.xyz = { /* тонкая обёртка над пакетом (DESK-4) */ };
  };
}
```

| Элемент | Правило |
|---|---|
| Метаданные | Первая строка, формат фиксирован; поля — имя, слот (или `—`), домен, классы, адресат. Домен и имя сверяются с путём, классы — с фактически определёнными `flake.modules.<класс>` (C3). Слот сверяется с каталогом (FEAT-7) |
| Один владелец | Файл владеет пакетом, юнитом, интеграцией своей фичи; конфиг приложения из реестра — dotfiles (DOT-3, SLOT-1) |
| Параметры | Только из `config.my.*` (FEAT-3). Констант хоста, имён пользователей, секретов нет |
| Зависимости | Фича **не импортирует** другую (ARCH-3). Если ей нужна другая фича, она объявляет `assertions` с понятным сообщением («фича X требует Y в составе хоста»). Это держит связь явной и при этом без импорта |
| Размер | ≲ 150 строк (ARCH-12): предупреждение при > 150, ошибка при > 250 |
| `mkForce`, `rec`, `with` на большой области | Только с комментарием-причиной (ARCH-13) |

### 3.4 Приватные части

Когда файл растёт, сначала делится **по границе контракта** на две фичи (пример: клиент туннеля и kill switch — разные фичи с разными контрактами). Только если часть нельзя выделить как самостоятельную фичу, она становится приватной.

**STR-6.** Приватная часть — файл или каталог с префиксом `_`, лежащий в каталоге домена рядом с владельцем: `_<владелец>-<часть>.<ext>` или `_<владелец>/…`. Правила:

1. Её подключает **только** владелец, относительным импортом (`import ./_tunnel-policy.nix`). Это не нарушает ARCH-3: часть — не фича.
2. Допустимое содержимое — данные и функции Nix, а также статические тексты, которые Nix вставляет в конфиг (например, текст правил фильтрации пакетов). Конфиги приложений из реестра сюда не относятся (DOT-3).
3. Каждая часть ≲ 150 строк; секретов нет.
4. Кастомный пакет, нужный одной фиче, — приватная часть владельца. При втором потребителе он становится отдельной фичей `pkg-<имя>` в подходящем домене с `perSystem.packages.<имя>` и общим overlay.

### 3.5 `core/` — каркас

| Файл | Содержимое |
|---|---|
| `framework.nix` | `systems`, подключение `flakeModules.modules` и `treefmt`, `_module.args.inputs` (без `specialArgs`, ARCH-8) |
| `options.nix` | Опции **внешнего** уровня: `my.users`, `my.theme.palette` (5.3 Архитектуры). Опции `my.host.*`, `my.ai.*`, `my.tunnel.*` объявляют `*-facts` соответствующих доменов |
| `lib.nix` | Чистые функции, нужные ≥ 2 фичам, и **хелперы путей** (STR-9). Функция в `lib.nix` появляется только при втором потребителе |
| `treefmt.nix` | Форматтеры и линтеры (OPS-1, DEV-8: один форматтер на тип файла) |
| `devshell.nix` | Оболочка разработки: `just`, `sops`, `age`, `nvd`, форматтеры, сканер секретов |
| `templates.nix` | Регистрация `flake.templates.<имя>` по каталогу `templates/` (DEV-3) |
| `checks-structure.nix` | Проверки раздела 8 (STR-C*) |
| `checks-docs.nix` | Сверка ID между `docs/architecture/*.md` и `docs/adr/*.md` (`scripts/check-doc-ids.sh`) |
| `checks-hosts.nix` | Сборка хоста класса `vm`, вычисление остальных хостов (OPS-2) |
| `checks-subsystems.nix` | Подключение `tests/*` (раздел 5.1) |

**STR-9.** Обращения к корню репозитория из фич идут **через хелперы** `lib.repo.secrets`, `lib.repo.assets`, `lib.repo.machines`, определённые в `core/lib.nix`. Цепочек `../../…` в фичах нет. Исключение — `hosts/<хост>.nix`, который подключает `../../machines/<хост>/hardware.nix`.

### 3.6 `presets/`

**STR-7.** Пресет — один файл с одним именем, содержащий **только** `imports` по каждому классу (FEAT-5). В каждом классе перечисляются лишь фичи, имеющие этот класс.

| Правило | Пояснение |
|---|---|
| Два вида пресетов | **Классы хоста** (`base`, `laptop`, `workstation`, `server`, `vm`) и **capability** (`desktop`, `development`, `office`, `media`, `gaming`, `ml`, `containers`), плюс `tunnel` (сетевая среда) и `user-base` (раздел 13). Вид указан в заголовке файла |
| Один владелец-пресет | Каждая пара «фича + класс» входит ровно в один пресет-владелец: nixos-часть оболочки может быть в `base`, а её homeManager-часть — в `user-base`, но один и тот же класс одной фичи в двух пресетах недопустим (не полагаемся на дедупликацию модулей). Аппаратные фичи (`gpu-*`) дополнительно подключаются прямо из хоста |
| Размер | ≲ 40 строк. Больше — домен слишком широк, делится capability |
| Состав изменяется только здесь | Добавить или убрать возможность = одна строка в пресете или хосте (цель 2 Архитектуры) |

### 3.7 `hosts/` и `machines/`

**STR-8.** Хост — файл `modules/hosts/<хост>.nix`: композиция пресетов плюс факты `my.host.*` (ARCH-4, HOST-1). Допустимо: `imports`; `my.host.*`; значения параметров `my.*` подсистем (`my.tunnel.policy.directCidrs`, `my.ai.inference.keepAlive`). Недопустимо: пакеты, сервисы, `mkForce` (FEAT-6).

```nix
# Хост: alice-laptop · класс: laptop
{ config, inputs, ... }:
let n = config.flake.modules.nixos; in {
  flake.nixosConfigurations.alice-laptop =
    inputs.nixpkgs.lib.nixosSystem { modules = [ n.alice-laptop ]; };
  flake.modules.nixos.alice-laptop = {
    imports = [
      n.base n.laptop n.tunnel                          # класс и сеть
      n.desktop n.development n.office n.media n.gaming n.ml n.containers
      n.gpu-integrated n.gpu-discrete n.gpu-hybrid      # аппаратное — составом (HOST-3)
      ../../machines/alice-laptop/hardware.nix
    ];
    my.host = { name = "alice-laptop"; class = "laptop"; users = [ "alice" ]; /* gpu, outputs, … */ };
  };
}
```

**`machines/<хост>/hardware.nix`** — единственный не-flake-parts файл вне `modules/` (ARCH-2, HOST-2): сгенерирован, без логики, первая строка — команда и дата генерации. Профиль `nixos-hardware`, если он есть, подключается из хоста. Физические характеристики (не привязаны к ОС) — в `docs/hosts/<хост>.md` и служат источником для `my.host.*`.

`hosts/_template.nix` — шаблон нового хоста (чек-лист 18.3 Архитектуры).

### 3.8 `users/`

**STR-8a.** Запись пользователя — файл `modules/users/<имя>.nix`, определяющий `my.users.<имя>` (`admin`, `capabilities`, режим dotfiles). Приватные факты пользователя — только в sops (SEC-2, USER-1). Имя пользователя встречается **только** в этом файле, в `my.host.users` хоста, в `secrets/users/<имя>.yaml` и в `.sops.yaml`; в путях и именах фич его нет (ARCH-17). Шаблон — `users/_template.nix`. Не путать: каталог `modules/users/` — данные пользователей, а фича `base/users.nix` создаёт по ним учётные записи (USER-3).

## 4. Данные и ресурсы вне `modules/`

### 4.1 `secrets/`

```
secrets/
├── README.md              # таблица «файл → ключи → фича-потребитель»; без значений
├── common.yaml            # общие для хостов (класс A)
├── hosts/<хост>.yaml      # секреты хоста
└── users/<имя>.yaml       # секреты пользователя (USER-7)
```

**STR-10.** Правила:

| Правило | Пояснение |
|---|---|
| Все файлы зашифрованы | Каждый YAML содержит блок `sops:`; проверка C9 |
| Нейтральные имена ключей | `<домен>.<роль>` без вендоров и адресатов (SEC-3). Пример: `net.endpoint`, а не имя оператора |
| Доступ к файлам | Только через хелпер `lib.repo.secrets` и объявление `sops.secrets` в фиче-владельце (SEC-4) |
| `.sops.yaml` — данные | Правило на каждый файл: `common`, `hosts/<хост>`, `users/<имя>`; recipients — только публичные ключи (SEC-7). Добавление хоста или пользователя меняет этот файл |
| Расшифрованные копии | Не создаются в дереве; шаблоны рендерятся при активации в каталог времени выполнения (VPN-CLI-2) |

```yaml
# .sops.yaml — схема (плейсхолдеры)
creation_rules:
  - path_regex: secrets/common\.yaml$
    key_groups: [{ age: [<ключ-админа>, <ключ-хоста-1>, <ключ-хоста-2>] }]
  - path_regex: secrets/hosts/<хост>\.yaml$
    key_groups: [{ age: [<ключ-админа>, <ключ-хоста>] }]
  - path_regex: secrets/users/<имя>\.yaml$
    key_groups: [{ age: [<ключ-пользователя>, <ключи-хостов-пользователя>] }]
```

### 4.2 `assets/`

Бинарные и текстовые ресурсы **Nix-владеемых** компонентов, которые не выражаются как значение внутри самой фичи (фон менеджера входа, значки загрузчика, структура `.ovpn`-профиля `vpn-client` — SEC-2 класс C, не секрет). Ресурсы пользовательских приложений — в dotfiles. Структура: `assets/<потребитель>/<файл>`. Файл ≤ 2 МБ; крупнее — внешний источник с хэшем. Происхождение и лицензия файла (если применимо) — в `assets/README.md`.

### 4.3 `templates/`

Один каталог на поддерживаемый язык или стек (DEV-3): `templates/<стек>/` с зафиксированным тулчейном, `flake.nix` проектного окружения, файлом автоактивации и коротким `README.md`. Регистрация — одна строка в `core/templates.nix`. Источники тулчейнов (оверлеи языков) — inputs шаблона, не системы (раздел 3 Архитектуры). В `modules/` шаблонов нет: у них свой `flake.nix`, и import-tree не должен его видеть.

## 5. `tests/`, `scripts/`, CI, `justfile`

### 5.1 `tests/`

Проверки **поведения**, которые нельзя выразить как `nix flake check` по формату: изоляция агентов, kill switch, проверка конфига туннеля.

```
tests/
├── <свойство>.nix         # функция { pkgs, nixosModules, … } → тест; один файл — одно свойство
└── fixtures/              # заведомо фиктивные значения корректного формата
```

| Правило | Пояснение |
|---|---|
| Подключение | Только через `modules/core/checks-subsystems.nix` |
| Именование | По проверяемому свойству, а не по фиче: `killswitch-fail-fast`, `agent-sandbox`, `tunnel-config` |
| Фикстуры | UUID из нулей, ключи формата, но не настоящие. Каталог `tests/fixtures/` внесён в исключения `.gitleaks.toml` — это единственное исключение сканера |

### 5.2 `scripts/`

**STR-11.** Скрипт допустим, если его вызывает `justfile`, CI или хук, и он решает ровно одну задачу. Логика сборки и конфигурации системы в скриптах недопустима — она в Nix. Первая строка — назначение и кто вызывает. Эталонный набор: `check-structure.sh`, `check-lock.sh` (A16), `check-doc-ids.sh`, `check-secrets.sh`, `dotfiles-clone.sh`, `hibernate-offset.sh` (R5.1), `new-feature.sh` (создаёт файл фичи из `modules/_templates/`; R9.2).

### 5.3 CI

```
.github/workflows/
├── check.yml        # формат, flake check, eval хостов, проверки STR, DOT-14, FEAT-8
├── build-vm.yml     # полная сборка хоста класса vm (HOST-4)
├── secrets.yml      # сканер секретов по коду и истории (A3)
└── update-lock.yml  # (опц.) PR с обновлением flake.lock
```

Один файл — одна цель; шаги вызывают рецепты `just` (CI и разработчик исполняют один и тот же код).

### 5.4 `justfile`

| Рецепт | Назначение |
|---|---|
| `bootstrap <хост>` | Установка на чистую машину (18.9 Архитектуры) |
| `check` | проверка формата (`nix fmt -- --ci`, файлы не правятся — OPS-2 требует именно проверки) + `flake check` (включает `check-structure`, C3 и `tests/*`) + `check-lock` (A16). Правит файлы отдельный рецепт `fmt` |
| `build <хост>` / `test <хост>` / `boot <хост>` | Сборка и применение без/с активацией (OPS-3) |
| `vm <хост>` | Виртуальная машина хоста (OPS-9) |
| `update [input]` | Обновление lock-файла и `nvd diff` |
| `dotfiles-clone` | Клонировать dotfiles в путь из `dotfiles.source`, если его там ещё нет (DOT-4) |
| `add-host <имя>`, `add-user <имя>`, `new-feature <домен> <имя>` | Создание из шаблонов вместе с правками `.sops.yaml` и пресета |
| `hibernate-offset` | Вычисление `my.host.resume.offset` (STO-5) |
| `sops-edit <файл>`, `sops-rekey` | Работа с секретами |

**STR-12.** Правила документации:

|---|---|
| Один источник | Каталог фич живёт в Архитектуре (раздел 6); в `modules/` README-файлов нет — иначе факт дублируется (ARCH-5) |

| Runbook | `runbook.md` остаётся единственной точкой входа (OPS-8); при росте процедуры выносятся в `runbook/<тема>.md` |
| Ссылки | Документация ссылается на правила по ID, а не на номера строк и не на пути, которые могут измениться |

## 7. Репозиторий dotfiles

Отдельный публичный репозиторий (DOT-1). Его структура — зеркало реестра `REGISTRY.md`, а не часть структуры `nixos-config`.

```
dotfiles/
├── README.md
├── REGISTRY.md              # реестр: приложение, целевой путь, версионная заметка, проверка
├── install.sh               # symlink'и + заглушки машинного слоя; --check-deps
├── machine.d.example/       # заглушки машинного слоя (DOT-5)
├── theme/
│   ├── palette.toml         # единственный источник палитры (DOT-9)
│   └── gen/                 # генератор colors.* (результат коммитится)
├── <приложение>/…           # по каталогу на приложение из реестра
├── ai/                      # общее для агентов: единый список MCP-серверов + генератор (AI-CTX-3)
├── net/                     # необязательная диагностика туннеля (VPN-OPS-2)
├── checks/                  # конфигурации линтеров и валидаторов (DOT-14)
└── .github/workflows/
```

| Правило | Пояснение |
|---|---|
| Структура внутри `<приложение>/` | Принадлежит приложению и дистрибутиву; `nixos-config` её не читает (кроме `theme/palette.toml`) |
| Адаптеры композитора | Отдельные файлы с штатным include в каталоге приложения (SLOT-4d): смена композитора не трогает основной конфиг |
| Скрипты оболочки | В каталоге своего приложения (DESK-9), без констант хоста |
| Агенты | Каждый агентный CLI — свой каталог в реестре (AI 2.4); `ai/` хранит только общее |
| Lock-файлы плагинов | В каталоге приложения (DOT-11) |
| Машинный слой | `~/.config/machine.d/` создаёт Nix, в репозитории только `machine.d.example/` (DOT-5) |

Граница с `nixos-config`: `nixos-config` ссылается на dotfiles **input-ом** (читает только `theme/palette.toml`, DOT-9) и через фичу `dotfiles-link`, которая симлинкует `~/.config/<app>` на рабочую копию пользователя (DOT-4). Конфигов приложений реестра в `nixos-config` не появляется (DOT-3).

## 8. Машинная проверка структуры

Проверки реализуются в `modules/core/checks-structure.nix` (C3 — нужен доступ к `config.flake.modules.*`) и `scripts/check-structure.sh` (остальные); проверка lock-файла (A16) — `scripts/check-lock.sh`. Запускаются командой `just check` и в `check.yml`.

| № | Правило | Проверка |
|---|---|---|
| C1 | STR-1: состав корня | Список элементов корня совпадает с таблицей раздела 2 |
| C2 | STR-4a: уникальность имён | Вывод `find modules -name '*.nix' -not -path '*/_*' -printf '%f\n' \| sort \| uniq -d` пуст |
| C3 | STR-5: метаданные | Имя и домен в первой строке совпадают с путём, перечисленные классы совпадают с определёнными; множество ключей `flake.modules.<класс>` равно множеству имён файлов (кроме `core`, `users`) |
| C4 | STR-2: глубина | `find modules -mindepth 3 -name '*.nix' -not -path '*/_*' -not -path 'modules/hosts/*' -not -path 'modules/users/*'` пуст |
| C5 | STR-4a: `default.nix` | `find modules -name default.nix` пуст |
| C6 | STR-5: размер | Предупреждение > 150 строк, ошибка > 250 |
| C7 | ARCH-3: нет импорта фич | `config.flake.modules` встречается только в `presets/`, `hosts/`, `base/users.nix`, `core/` |
| C8 | STR-6: приватные части | Каждый `_<владелец>-…` существует рядом с `<владелец>.nix` и упомянут только в нём |
| C9 | STR-10: секреты | Каждый файл в `secrets/` содержит блок `sops:`; значений в `secrets/README.md` нет |
| C10 | FEAT-8, STR-7 | Каждая пара «фича + класс» входит ровно в один пресет-владелец или в хост (ни ноль — неиспользуемая фича, ни больше одного); пресеты содержат только `imports`. Шаблоны `_template.nix` составами не считаются |
| C11 | FEAT-7 | Слот из метаданных присутствует в каталоге Архитектуры |
| C12 | DOT-14 | В `modules/` нет генераторов конфигов для приложений реестра dotfiles (`programs/services.<app>.{settings,extraConfig,…}`, `xdg.configFile.<app>`, `home.file.".config/<app>"`). Разрешены `enable`, `package` и `programs.zsh.shellInit` (DOT-12). Вторая половина DOT-14 — «нет `/nix/store` в dotfiles» — проверяется в CI репозитория dotfiles |

```sh
# Пример: C2 и C9 (scripts/check-structure.sh)
dups=$(find modules -name '*.nix' -not -path '*/_*' -printf '%f\n' | sort | uniq -d)
[ -z "$dups" ] || { echo "Повтор имён:"; echo "$dups"; exit 1; }
unenc=$(grep -L '^sops:' secrets/*.yaml secrets/*/*.yaml 2>/dev/null)
[ -z "$unenc" ] || { echo "Незашифрованы:"; echo "$unenc"; exit 1; }
```

## 9. Куда класть новое

**Порядок вопросов** (первый «да» даёт ответ):

1. Это **секрет или приватный факт**? → `secrets/…` (4.1) либо вне репозитория (класс D, SEC-2).
2. Это **конфиг приложения из реестра**? → репозиторий dotfiles (раздел 7).
3. Это **физические данные железа**? → `docs/hosts/<хост>.md` и `machines/<хост>/hardware.nix`.
4. Это **данные пользователя или хоста** (кто, какие возможности, какие факты)? → `users/`, `hosts/`.
5. Это **не Nix-модуль** (бинарник, шаблон проекта, скрипт, тест)? → `assets/`, `templates/`, `scripts/`, `tests/` (раздел 4–5).
6. Это **часть одной фичи**, которую нельзя выделить? → приватная часть (3.4).
7. Иначе — **фича**: домен по 3.1, имя по 3.2, пресет по 3.6.

| Что добавляем | Куда | Что ещё |
|---|---|---|
| Пакет пользователя | В фичу-владельца (`home.packages`) | — (ARCH-11) |
| Системный пакет | В фичу-владельца (`environment.systemPackages`) или `services.*` | — |
| Новая программа | `modules/<домен>/<слот>-<р>.nix` | Пресет, каталог (FEAT-7), при необходимости dotfiles + `REGISTRY.md` |
| Замена реализации слота | Новый файл рядом; строка в пресете | dotfiles-каталог и реестр (18.5 Архитектуры) |
| Свежая версия из нестабильного канала | Overlay в файле фичи, комментарий-причина | `nixpkgs-unstable` — единственный лишний input (ARCH-14) |
| Параметр хоста | `my.host.*` в `hosts/<хост>.nix`; опция — в `host-facts` | — |
| Новая опция `my.*` | В `*-facts` своего домена; уровень «внешний» — `core/options.nix` | Реестр 5.3 Архитектуры |
| Второй потребитель общей функции | `core/lib.nix` | — |
| Кастомный пакет | Приватная часть владельца (3.4) | — |
| Новая capability | `presets/<имя>.nix` | Словарь USER-4, записи пользователей |

## 10. Сценарии изменений и их набор файлов

Цель K2: типовое изменение — не более трёх **существующих** файлов; прочее — **создаваемые** файлы.

| Сценарий | Меняем (существующее) | Создаём |
|---|---|---|
| Добавить пакет в существующую возможность | 1: фича-владелец | — |
| Добавить программу | 2: пресет, каталог Архитектуры | фича; при реестре — каталог dotfiles |
| Заменить реализацию слота (например, композитор) | 1–2: пресет, `REGISTRY.md` | фича-реализация, каталог dotfiles (DESK-10) |
| Новый хост | 1: `.sops.yaml` | `hosts/<х>.nix`, `machines/<х>/hardware.nix`, `secrets/hosts/<х>.yaml`, `docs/hosts/<х>.md` |
| Новый пользователь | 3: `hosts/<х>.nix` (`my.host.users`), `.sops.yaml`, при своём источнике dotfiles — `flake.nix` | `users/<имя>.nix`, `secrets/users/<имя>.yaml` |
| Новый язык или стек | 1: `core/templates.nix`; при необходимости `lsp-global` | `templates/<стек>/` |
| Новый секрет | 2: фича-владелец (объявление), `secrets/README.md` | значение — командой `sops-edit` |
| Смена адреса выхода туннеля | 0 в коде: только значение в sops (VPN-RES-3) | — |
| Новая capability | 1: запись пользователя | `presets/<имя>.nix` |
| Изменить палитру | 0 в `nixos-config`; `flake.lock` через `just update` | правка в dotfiles `theme/palette.toml` |
| Изменить раскладку клавиатуры | 1: `base/locale-keyboard.nix` | — |
| Подключить монитор | 1: `hosts/<х>.nix` (`my.host.outputs`) | — |
| Изменить конфиг приложения | 0 в `nixos-config` | правка в dotfiles |
| Обновить версии | `flake.lock` | — |
| Новая подсистема (как AI или VPN) | 1–2: каталог Архитектуры, при новом домене — раздел 3.1 | `<подсистема>-facts.nix`, фичи, пресет, `docs/architecture/<ПОДСИСТЕМА>.md`, ADR |

## 11. Отклонённые структуры

| Вариант | Почему отклонён |
|---|---|
| Классическое разделение `hosts/` + `modules/nixos/` + `modules/home/` + `home-manager/<имя>/` | Одна возможность размазана по двум деревьям; значения идут через `specialArgs` (ARCH-8); имя пользователя попадает в пути (ARCH-17); возможность не отключается одной строкой |
| Плоский `modules/` без доменов | ≈ 75 файлов в одном каталоге; нарушается K1 |
| Глубокие деревья (`desktop/hyprland/bar/…`) | Путь перестаёт быть адресом; замена реализации затрагивает несколько каталогов; имена файлов повторяются (`default.nix`) |
| Подкаталог на слот (`desktop/bar/{xyz,abc}.nix`) | Уровень вложенности без выигрыша; ломает правило двух уровней и уникальность имён |
| Группировка по capability (`modules/gaming/` с драйвером GPU) | Смешивает «что это» и «кому нужно»; фича теряет место при смене состава |
| `lib/`, `overlays/`, `pkgs/` в корне | Свалки (ARCH-11): пакет и overlay принадлежат фиче; общая функция — `core/lib.nix` по правилу второго потребителя |
| Каталог `hosts/<имя>/default.nix` рядом с `modules/` | Второй механизм импорта; хост перестаёт быть модулем и выпадает из проверок |
| `home-manager/<имя>/programs/<app>/` с конфигами | Нарушает ARCH-15 и DOT-3: конфиг приложения становится непереносимым |
| `dotfiles` как подкаталог `nixos-config` | Разный жизненный цикл; невозможна установка на не-Nix систему без клонирования всей конфигурации (DOT-1) |
| README в каждом домене | Дублирует каталог Архитектуры; расходится с ним (ARCH-5) |
| Монорепозиторий с отдельным flake на домен | Рост числа lock-файлов и `follows`; нарушает A16 |

## 12. Масштабирование

| Рост | Порог | Действие |
|---|---|---|
| Фич в домене | > 15 | Разделить домен: запись каталога и ADR (STR-3) |
| Размер файла | > 150 строк | Делить по границе контракта; затем — приватная часть (3.4) |
| Размер пресета | > 40 строк | Разделить capability |
| Хосты | > 15 | `hosts/<группа>/<хост>.nix`; уникальность имён сохраняется |
| Пользователи | > 15 | `users/<группа>/<имя>.nix` |
| Второй мейнтейнер | — | Структура не меняется: правила проверяются CI |
| Не-NixOS цели | — | Вне охвата Архитектуры; отдельный репозиторий |

## 13. Требуемые уточнения Архитектуры

Документ вводит три уточнения, не меняющие корневые принципы; они оформляются записями реестра ADR (OPS-7).

| ID | Решение | Затрагивает |
|---|---|---|
| ADR-31 | **Структура репозитория — этот документ.** Схема раздела 4 Архитектуры становится кратким обзором со ссылкой на STRUCTURE.md; добавлены: `assets/`, `tests/`, `scripts/`, `CLAUDE.md`, `.claude/`, `docs/architecture/` (в том числе `ROADMAP.md`), `docs/hosts/`, `modules/_templates/`; правило уникальных имён файлов (STR-4a); приватные части `_` могут подключаться владельцем (уточнение ARCH-2); имена реализаций слотов по A.3 (STR-4b) | Разделы 4 и 6, ARCH-2, FEAT-1, OPS-8 |
| ADR-32 | **`user-base` — HM-пресет базового окружения пользователя**, подключаемый фичей `users` **каждому** пользователю независимо от capability. Состав — HM-классы фич этого базиса: `dotfiles-link`, `user-dirs`. Оболочка, VCS и `env-manager` дают тот же результат через nixos-класс в пресете `base` (системные пакеты доступны каждому пользователю хоста), поэтому HM-дубля у них нет (ARCH-5) | USER-3 |

В рамках ADR-31 записи каталога раздела 6, перечисленные в A.3 как «слот → реализация» (`containers`, `env-manager`, `office-suite`, `video-player`, …), получают суффикс `-<р>`; capability `containers` остаётся именем пресета.

Обоснование ADR-32: сейчас USER-3 подключает HM-модули только по capability, а оболочка, VCS и `dotfiles-link` не привязаны ни к одной из них; пользователь без `development` (например, администратор headless-хоста) остался бы без оболочки и без конфигов.

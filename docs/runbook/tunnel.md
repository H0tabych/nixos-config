# Runbook: туннель — upstream для LLM

Конкретизация VPN_SUBSYSTEM.md §4.7 (VPN-LLM-1…6) и роадмапа R3.6/S4.
Относится к выходу (серверу туннеля), настраивается через панель — не
NixOS-система, в этом репозитории не декларируется (VPN_SUBSYSTEM.md P.1,
P.7). Данные учётной записи upstream и сведения об операторе — секрет
и приватный журнал, здесь не хранятся (P.6/P.7); здесь — только список
доменов (публичные данные, VPN-LLM-3).

## Список доменов

Правила в маршрутизации выхода, **в этом порядке** (правило API — выше
правила upstream; VPN-LLM-3, регресс R-02):

| № | Правило | Домены | outboundTag |
|---|---|---|---|
| 1 | API-хосты (мимо upstream) | `api.anthropic.com`, `api.openai.com` | `direct` |
| 2 | Upstream (веб-интерфейсы) | `domain:claude.ai`, `claude.com`, `claudeusercontent.com`, `chatgpt.com`, `oaistatic.com`, `oaiusercontent.com` | `warp` (upstream) |

Список — отправная точка (P.2), уточняется по логам. Корневые домены
провайдеров (`anthropic.com`, `openai.com`) в правило upstream **не входят** —
иначе они захватят `api.*` и сломают VPN-LLM-1.

## Процедура изменения (VPN-SRV-7)

1. Резервная копия текущего конфига маршрутизации выхода.
2. Правка в панели: правило 1 (API) выше правила 2 (upstream), см. таблицу.
3. Проверка конфига ядром (панель/перезапуск сервиса без ошибок; неизвестный
   гео-тег останавливает выход для всех клиентов — не использовать гео-теги
   для LLM-доменов, только явные `domain:`).
4. Применение.
5. Клиентский smoke-тест: базовая проверка связности через туннель после
   изменения (VPN-A5 в части, применимой к M1).
6. Откат к резервной копии при сбое любого из пп. 3–5.

## Приёмка (VPN-A12, VPN-LLM-6)

`curl` **не доказывает доступность** защищённых веб-интерфейсов — отказ
может приходить независимо от адреса. Приёмка — только так:

1. **В реальном браузере** открыть веб-интерфейс целевого LLM-сервиса
   (claude.ai и/или chatgpt.com) и выполнить вход, без цикла проверки.
2. Выполнить API-вызов через шлюз (к `api.anthropic.com`/`api.openai.com`)
   и убедиться, что он успешен.
3. Временно отключить/удалить upstream-звено (правило 2) на выходе и
   повторить API-вызов — должен остаться успешным (доступ по API-ключам
   не зависит от upstream, VPN-LLM-1/2).
4. Убедиться, что отключение upstream не затронуло прочий трафик.
5. Вернуть правило upstream (откат — см. процедуру выше).

# Runbook: туннель

Реестр отступлений от правил подсистемы, upstream для LLM, список доменов и
операционные процедуры режима M2 (портал, откат kill switch, клиенты, выход).

## Реестр отступлений (VPN-CLI-3)

VPN-CLI-3 требует, чтобы клиент проверял подлинность выхода всеми средствами
протокола, включая постквантовую подпись, и чтобы клиент без такой проверки был
записан здесь — с клиентом, причиной и сроком пересмотра.

| Клиент | Что не выполняется | Причина | Срок пересмотра |
|---|---|---|---|
| `tunnel-xray` на `sgms-laptop` (xray-core) | `mldsa65Verify` пуст — постквантовая подпись выхода не проверяется | Ядро клиента проверку **поддерживает**; подпись не выпускает сам выход, то есть не выполнен VPN-SRV-3 на сервере. Поэтому это отступление сервера, а не исключение по VPN-CLI-3 для неподдерживающего клиента | До Gate G5 (этап 5). Снимается так: включить подпись на выходе (VPN-SRV-3) → положить ключ проверки в `secrets/common.yaml` → заполнить `mldsa65Verify` в `modules/network/tunnel-xray.nix` → убрать строку из этой таблицы |
| `backup` на `sgms-laptop` (R5.2) | STO-8 «кэши исключены» — `~/.cache` попадает во внешнюю копию | `~/.cache` лежит внутри подтома `home`, а `btrfs send/receive` не умеет исключать подкаталоги. В локальных снимках это почти бесплатно (CoW), во внешней копии — реальный объём | Снимается выделением `~/.cache` в отдельный подтом, то есть правкой разметки (`layout`, **PNR-2**). Пересмотреть при следующей переустановке |
| `tunnel-xray` на `sgms-laptop` (R5.4) | Режим M2 ещё не включён на машине → NET-8 (kill switch обязателен в M2), VPN-A5/A7/A8/A9, VPN-MOD-7 не выполняются; система работает в M1 с его ограничениями (VPN-MOD-2) | Реализация проверена только в ВМ (ADR-41). Включение ждёт R9.6 и прогона гейта 7.3 на машине | Гейт 7.3 на машине, раздел «Переход на M2» ниже |

Пока первая строка здесь, критерий R3.2 «проверка постквантовой подписи»
выполнен не полностью, и это учтено в разделе 8 ROADMAP.

## Переход на M2 (R5.4)

**Вердикт гейта 7.3 от 2026-10-14 отозван (ADR-41).** Причиной тогда записали
отсутствие IPv4 на устройстве tun. Контрольные прогоны показали, что без адреса
туннель работает, а сеть терялась из-за дефектов конфигурации. Реализация проверена
в ВМ (`tests/tunnel-m2.nix`). На машине режим остаётся M1 до прогона гейта.

### Перед включением

1. Выполнен R9.6: без маршрута `direct` отказ выхода в M2 повторит инцидент 2026-11-04.
2. На текущей версии ядра туннеля (M1) работают браузер, `nix build`, Docker и
   корпоративный VPN.
3. Версии клиента и выхода совместимы (VPN-CLI-12). При отпечатке `chrome` оба смешанных
   сочетания 26.3.27 и 26.10.31 проверены в ВМ, порядок обновления не важен. Reality
   26.9.8+ отвергает ClientHello без X25519MLKEM768: при другом отпечатке проверить отдельно.

### Включение

Включение обратимо на каждом шаге: `just test` применяет немедленно и **без**
перезагрузки, загрузчик не трогается. Перед ним таймер автоотката, потому что при
потере сети снять его может быть нечем, а прежняя система уже в store и сеть для
отката не нужна.

```sh
# 1. modules/hosts/sgms-laptop.nix: в блоке my.tunnel добавить mode = "m2";
just build sgms-laptop && nvd diff /run/current-system result

# 2. Автооткат через 5 минут, если его не отменить.
PREV=$(readlink -f /run/current-system)
sudo systemd-run --unit=m2-revert --on-active=5min "$PREV/bin/switch-to-configuration" test
just test sgms-laptop

# 3. Проверки. Прокси-переменные из окружения убирать обязательно, иначе измеряется прокси.
systemctl status tunnel-routes.service tunnel-xray.service
ip -4 rule show                    # приоритеты 32000 (suppress_prefixlength) и 32001 (not fwmark)
ip -4 route show table 7777        # default dev tunnel0 и unreachable
resolvectl status | head -5        # DNS Servers: 198.18.0.2
env -u http_proxy -u https_proxy -u all_proxy -u HTTP_PROXY -u HTTPS_PROXY -u ALL_PROXY \
    curl -s https://ifconfig.me; echo

# 4. Всё хорошо — отменить автооткат. Постоянным поколением делает только этот шаг:
sudo systemctl stop m2-revert.timer
just boot sgms-laptop
```

`ping` через туннель доступность не доказывает: на ICMP Echo отвечает сам TUN. TCP-соединение
к любому адресу тоже устанавливается сразу, а ошибка приходит следом. Проверять надо запросом.

### Откат

| Ситуация | Что делать |
|---|---|
| Сеть пропала в первые 5 минут | Дождаться автоотката или выполнить `sudo $PREV/bin/switch-to-configuration test` |
| Позже | `my.tunnel.mode = "m1"`, `just build`, `just test`; либо прежнее поколение из меню загрузчика (`docs/runbook/storage.md`, раздел 4) |
| Только временно нужна сеть мимо туннеля | Процедура 1 ниже. Просто удалить таблицу kill switch не поможет: трафик всё равно уйдёт в туннель |

### Гейт 7.3 (VPN_SUBSYSTEM.md §7.3)

| № | Критерий | В ВМ | На машине |
|---|---|---|---|
| M2-1 | TCP/UDP/DNS, QUIC откатывается на TCP | TCP, UDP, DNS: да | QUIC: сайт с HTTP/3 открывается в браузере. Vision отвергает UDP/443, браузер должен уйти на TCP без заметной задержки |
| M2-2 | Нет петель | Да, в том числе без маршрута по умолчанию | — |
| M2-3 | Переживает смену сети | Смена шлюза без перезапуска клиента | Wi-Fi ↔ Ethernet ↔ точка доступа: `systemctl show -p MainPID,NRestarts tunnel-xray` не меняется |
| M2-4 | Три цикла гибернации | — | Три раза `systemctl hibernate`, туннель восстанавливается ≤ 30 с (VPN-A9) |
| M2-5 | DNS без обхода | Да, на захвате у провайдера | `sudo tcpdump -ni <линк> port 53`: только `dnsDirect` |
| M2-6 | DynamicUser, минимальные права | Да | — |
| M2-7 | Нагрузка на CPU приемлема | Сравнение версий (ADR-41) | `systemd-cgtop` под целевой скоростью (VPN-A10) |
| M2-8 | Контейнеры покрыты, `bypass.units` работает | Контейнеры: да. `bypass.units`: не реализован | Торрент-клиент, см. ниже |
| M2-9 | Версия выдерживает M2-1…M2-8 и M2-10 | 26.3.27 — нет (M2-1), поэтому 26.10.31 из нестабильного канала (VPN-CLI-11) | Итог остальных пунктов |
| M2-10 | `direct` в M2 | — | После R9.6 |

Ещё на машине: VPN-A7 (тесты утечек в браузере, включая WebRTC), VPN-A8 (`systemctl stop tunnel-xray`:
отказ ≤ 2 с, в захвате на физическом интерфейсе ничего), VPN-A10, корпоративный VPN поверх туннеля
(VPN-INT-5, D6: `sudo systemctl start openvpn-corporate`, затем ресурс из зоны `metasfera.ru`) и
работа с NetworkManager: в ВМ сеть настроена статически.

**Открытый вопрос M2-8, VPN-A6.** В M2 трафик Transmission идёт в туннель, а шифрованный BitTorrent
правилом `protocol` не определяется и уйдёт на выход. Обход `bypass.units` требует системного юнита, а
клиент сейчас запускается из сессии. Решение принимает владелец до гейта.

Результаты — в эту таблицу и ADR-41 (OPS-7).

### Контрольные прогоны

Каждый дефект прежней конфигурации можно вернуть по одному: `tests/tunnel-m2.nix` принимает аргумент
`variant`. Результаты 2026-11-05 — в ADR-41. Пример, нет upstream у резолвера:

```sh
nix build --impure --no-link -L --expr '
  let
    f = builtins.getFlake "git+file://'"$PWD"'";
    pkgs = f.inputs.nixpkgs.legacyPackages.x86_64-linux;
  in
  import ./tests/tunnel-m2.nix {
    inherit pkgs;
    inherit (pkgs) lib;
    inputs = f.inputs;
    nixosModules = f.modules.nixos;
    variant = {
      name = "no-dns";
      client.services.resolved.settings.Resolve.DNS = pkgs.lib.mkForce [ ];
      script = "print(client.execute(\"curl -sS --max-time 10 http://foreign.test/\"))";
    };
  }'
```

### Ограничения M1, пока M2 не включён (VPN-MOD-2)

Покрыты только процессы, читающие прокси-переменные или настроенные явно.
**Не покрыты:** демоны, контейнеры, Nix, агенты. **Kill switch в M1 не
работает** (NET-8 относится к M2) — при отказе туннеля прокси-осведомлённые
приложения получают отказ, остальные идут напрямую. Критерии VPN-A5, A7
(полностью), A8, A9 на M1 **не достижимы**.

**Подтверждённый случай (R8.1/R8.2, 2026-10-25, `sgms-laptop`).** При проверке
`compute-cache` (ML-2) бинарный кэш CUDA (`cache.nixos-cuda.org`) был
недоступен из-под `nix build`/nix-daemon — запросы `.narinfo` стояли на
`< 1 байт/с` и истекали по таймауту, вплоть до падения соединения с
nix-daemon на части попыток. Промежуточная гипотеза («слабый лимит
соединений на стороне кэша») не подтвердилась: понижение
`nix.settings.http-connections` до 8 не помогло, сервер стал явно отказывать
в соединении на 4-й повторной попытке — похоже на анти-абузную защиту, а не
мягкий лимит. Решающий замер — тот же параллелизм (25 запросов), тот же
хост, тот же момент, но разным маршрутом:

| Маршрут | Успешно |
|---|---|
| через локальный прокси туннеля (`127.0.0.1:10809`) | 25/25 |
| напрямую (`curl --noproxy '*'`) | 16/25, 9 зависло |

Причина — не кэш и не M1 как таковой, а то, что прямой путь из российской
сети ограничивает параллельные подключения именно к этому внешнему хосту;
`nix-daemon` просто не входит в число процессов, читающих прокси-переменные
(NET-7), и в M1 никем не покрыт. **Исправлено ADR-039**: `nix-daemon.service`
получает те же прокси-переменные отдельным, явно временным механизмом
(`modules/network/_tunnel-xray-nix-proxy.nix`) до перехода на M2 — тогда
покрытие станет общим и это исключение снимается (условие снятия — в ADR).
**AI-CC-3 (покрытие кэша CUDA) проверяется живой сборкой** — содержимому
кэша замер не противоречил, проблема была в маршруте запросов.

### Методические выводы 2026-10-14

Выводы 1, 2 и 4 остаются в силе, 3 и 5 пересмотрены (ADR-41).

1. **Новые поля `tun`-инбаунда зависят от версии.** В 26.3.27 нет ни адресации, ни
   автомаршрутизации, в 26.10.31 они есть, но не используются (ADR-41).
2. **`xray run -test` неизвестные поля не ловит.** Неизвестные поля `settings` ядро
   игнорирует **молча**: конфиг с заведомо бессмысленным полем проходит проверку.
   Значит `run -test` подтверждает только общий синтаксис. Поведение проверяет
   `tests/tunnel-m2.nix`.
3. **Пересмотрено.** Тогда сеть терялась сразу по нескольким причинам, и по симптому они
   неразличимы. Один симптом нельзя приписывать одной причине без контрольного прогона.
   Первым проверять надо в изолированной сети, а не на единственной рабочей.
4. **Ложная тревога, снята:** казалось, что kill switch пропускает трафик мимо туннеля
   (`curl` до внешнего адреса проходил при активной таблице). Причина была в тестовой
   среде: в оболочке остались прокси-переменные режима M1, поэтому `curl` уходил на
   `127.0.0.1:10809`, а дальше xray — со своей меткой. При проверке M2 прокси-переменные
   из окружения надо убирать, иначе измеряется не то.
5. **Отозвано.** Вывод «маршрут через устройство без IPv4-адреса не работает» неверен:
   ядро берёт адрес источника с другого интерфейса, и туннель работает на обеих версиях.

## Процедуры режима M2 (R5.5)

> Все действия выполняет человек. Ассистент правила kill switch не применяет и
> `sudo` не запускает (ROADMAP W10).
>
> **Общий принцип (VPN-KS-9):** ошибка в правилах не должна отрезать
> восстановление. Если сеть пропала — консоль и откат поколения доступны
> всегда: `nixos-rebuild list-generations`, затем загрузка прежнего поколения
> из меню systemd-boot (`docs/runbook/storage.md`, раздел 4).

### 1. Портал авторизации в публичной сети (VPN-KS-6)

Публичный Wi-Fi требует авторизации в браузере, а в M2 весь трафик идёт в туннель и
kill switch режет остальное. Поэтому снимать надо и таблицу, и правила маршрутизации.
Только **вручную, с ограничением по времени и автоматическим возвратом**; факт снятия
попадает в журнал.

```sh
# Автовозврат через 10 минут, даже если про него забыли (требование KS-6).
sudo systemd-run --unit=tunnel-portal-return --service-type=oneshot --on-active=10min \
    --description="Возврат kill switch и маршрутов туннеля после портала (KS-6)" \
    /bin/sh -c 'systemctl start tunnel-routes.service && systemctl reload nftables.service'

sudo systemctl stop tunnel-routes.service
sudo nft delete table inet killswitch
logger -t killswitch "KS-6: таблица и маршруты туннеля сняты вручную на 10 минут"

# Резолвер портала: в M2 DNS из DHCP не используется (VPN-DNS-2).
sudo resolvectl dns <линк> <шлюз сети>
sudo resolvectl default-route <линк> yes

# → авторизоваться в портале, затем вернуть всё, не дожидаясь таймера:
sudo resolvectl revert <линк>
sudo systemctl start tunnel-portal-return.service
sudo nft list table inet killswitch     # убедиться, что таблица снова на месте
```

После возврата — проверить, что внешний адрес снова адрес выхода, а не
провайдера (VPN-A4).

**Если забыли вернуть:** таймер `tunnel-portal-return` сработает сам; проверить
`systemctl list-timers tunnel-portal-return`. Настройки DNS на линке он не снимает:
`sudo resolvectl revert <линк>`.

Снятие и возврат таблицы и правил проверены в ВМ. Шаг с резолвером портала проверяется
вживую на R5.5.

### 2. Откат kill switch (VPN-KS-9)

Когда правила оказались неверными и сеть недоступна. Само удаление таблицы сеть не
вернёт: трафик по-прежнему идёт в туннель, поэтому быстрый путь — процедура 1.

```sh
# Правильно — вернуть режим m1 одним параметром: kill switch, правила маршрутизации и
# dns-resolver включаются по my.tunnel.mode, в m1 они неактивны
#   modules/hosts/sgms-laptop.nix: my.tunnel.mode = "m1";
just build sgms-laptop && just test sgms-laptop

# Если и это не помогло — загрузиться прежним поколением (storage.md, раздел 4)
```

### 3. Добавление и отзыв клиента

Идентификаторы клиентов — секреты (SEC-5), в git и в чат не попадают.

```sh
# Добавить: сгенерировать идентификатор на выходе, положить в секреты хоста
just sops-edit secrets/hosts/<хост>.yaml     # tunnel.clientId, tunnel.shortId
just sops-rekey                              # если менялся список получателей
just build <хост> && just test <хост>

# Отозвать: удалить идентификатор на стороне ВЫХОДА (клиентский конфиг сам по
# себе доступ не даёт), затем убрать секреты хоста и перевыпустить остальным
just sops-edit secrets/hosts/<хост>.yaml
```

Отзыв считается выполненным только после проверки: с отозванным
идентификатором соединение не устанавливается.

### 4. Замена адреса выхода

Адрес выхода — секрет (SEC-4), в `/nix/store` попадает только путь.

```sh
just sops-edit secrets/common.yaml   # tunnel.endpoint (+ serverKey/serverName при смене выхода)
just build sgms-laptop && nvd diff /run/current-system result
just test sgms-laptop
```

Проверка: внешний адрес сменился, утечек нет, резолвер отвечает только через
туннель.

**Важно:** kill switch опознаёт трафик клиента по метке
(`my.tunnel.killswitch.mark`), а не по адресу выхода — поэтому смена адреса
правил не трогает и повторной правки таблицы не требует (VPN-KS-2).

## Upstream для LLM

Конкретизация VPN_SUBSYSTEM.md §4.7 (VPN-LLM-1…6) и роадмапа R3.6/S4.
Относится к выходу (серверу туннеля), настраивается через панель — не
NixOS-система, в этом репозитории не декларируется (VPN_SUBSYSTEM.md P.1,
P.7). Данные учётной записи upstream и сведения об операторе — секрет
и приватный журнал, здесь не хранятся (P.6/P.7); здесь — только список
доменов (публичные данные, VPN-LLM-3).

## Список доменов

Правила в маршрутизации выхода, **в этом порядке** (правило API — выше
правила upstream; VPN-LLM-3, регресс R-02):

| № | Правило | Домены | outboundTag |
|---|---|---|---|
| 1 | API-хосты (мимо upstream) | `api.anthropic.com`, `api.openai.com` | `direct` |
| 2 | Upstream (веб-интерфейсы) | `domain:claude.ai`, `claude.com`, `claudeusercontent.com`, `chatgpt.com`, `oaistatic.com`, `oaiusercontent.com` | `warp` (upstream) |

Список — отправная точка (P.2), уточняется по логам. Корневые домены
провайдеров (`anthropic.com`, `openai.com`) в правило upstream **не входят** —
иначе они захватят `api.*` и сломают VPN-LLM-1.

## Процедура изменения (VPN-SRV-7)

1. Резервная копия текущего конфига маршрутизации выхода.
2. Правка в панели: правило 1 (API) выше правила 2 (upstream), см. таблицу.
3. Проверка конфига ядром (панель/перезапуск сервиса без ошибок; неизвестный
   гео-тег останавливает выход для всех клиентов — не использовать гео-теги
   для LLM-доменов, только явные `domain:`).
4. Применение.
5. Клиентский smoke-тест: базовая проверка связности через туннель после
   изменения (VPN-A5 в части, применимой к M1).
6. Откат к резервной копии при сбое любого из пп. 3–5.

## Приёмка (VPN-A12, VPN-LLM-6)

`curl` **не доказывает доступность** защищённых веб-интерфейсов — отказ
может приходить независимо от адреса. Приёмка — только так:

1. **В реальном браузере** открыть веб-интерфейс целевого LLM-сервиса
   (claude.ai и/или chatgpt.com) и выполнить вход, без цикла проверки.
2. Выполнить API-вызов через шлюз (к `api.anthropic.com`/`api.openai.com`)
   и убедиться, что он успешен.
3. Временно отключить/удалить upstream-звено (правило 2) на выходе и
   повторить API-вызов — должен остаться успешным (доступ по API-ключам
   не зависит от upstream, VPN-LLM-1/2).
4. Убедиться, что отключение upstream не затронуло прочий трафик.
5. Вернуть правило upstream (откат — см. процедуру выше).

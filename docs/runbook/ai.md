# Runbook — ML и агенты

Восстановление, смена ключей, очистка журналов, перегрузка моделей, измеренные
характеристики и журнал приёмки подсистемы (AI-OPS-5, AI-RES-10, S7).

Владельцы механизмов: `ai/inference-service-ollama` (инференс, `inference-release`,
гибернация), `ai/llm-gateway` (шлюз, секреты пользователя), `ai/agents-tools`
(лаунчер и песочница), `ai/code-context` (MCP и структурный поиск).

> Команды с `sudo`, `just test`/`just boot` и удаление данных выполняет человек
> (ROADMAP W10). Значения ключей здесь не приводятся и в чат не передаются.

## 1. Восстановление

### Инференс

```sh
systemctl status ollama.service
curl -s http://127.0.0.1:11434/api/version
curl -s http://127.0.0.1:11434/api/ps       # загруженные модели; size_vram = size → на GPU
```

Инференс ушёл на CPU или не видит GPU после resume (AI-INF-6): штатно это чинит
`inference-post-resume`. Запустить его вручную:

```sh
sudo systemctl start inference-post-resume.service
```

Он останавливает сервис и перезагружает модуль `nvidia_uvm`. Откат не нужен: сервис
поднимается заново, модель загружается по требованию.

### Шлюз

Шлюз — системная служба на пользователя (ADR-45): `llm-gateway-<имя>` (`DynamicUser`,
состояние в `/var/lib/private/llm-gateway-<имя>/`, root читает, пользователь нет).

```sh
systemctl status llm-gateway-$USER
journalctl -u llm-gateway-$USER -n 50     # журнал системной службы, нужны права на чтение журнала
```

Юнит не должен быть `failed` и без облачных ключей (AI-A14): провайдер с пустым секретом
вычёркивается, его роли отвечают ошибкой. Справочник цен (по нему считаются бюджеты) — файл из
хранилища, собранный из `my.ai.gateway.providers.<id>.prices` (ADR-49), его служба не скачивает.
Справочник параметров моделей первый старт на новом состоянии скачивает с сайта апстрима: без сети
(`direct` с kill switch) служба повторяет попытки каждые 5 с и поднимется, когда сеть появится;
дальше кэш лежит в состоянии.
Единственный источник настроек — `config.json` (Nix и sops, `source_of_truth`), он
пересобирается при каждом старте. Если база повреждена, отложите её, а не удаляйте (root):

```sh
sudo systemctl stop llm-gateway-$USER
sudo mv /var/lib/private/llm-gateway-$USER/config.db /var/lib/private/llm-gateway-$USER/config.db.bak
sudo systemctl start llm-gateway-$USER
```

Откат: остановить юнит и вернуть файл на место.

**Ключи доступа** — по паре «агент × режим»: файлы `/run/llm-gateway/<имя>/<агент>-<режим>`
(`dsh-online`, `dsh-offline`; у агента по подписке ключа нет), права `root:<группа> 0440`,
создаются при старте службы, исчезают при остановке. Постоянные: хранятся в состоянии службы и
не меняются при перезапуске. Ротация одного ключа (root): удалить
`/var/lib/private/llm-gateway-<имя>/keys/<агент>-<режим>` и перезапустить службу; запущенные
сессии агента потеряют авторизацию. Вход в управляющий API: учётные данные
`keys/admin-user` и `keys/admin-pass` в том же каталоге (читает root).

**Проверка живым запросом** (роль через шлюз; ключ не печатается):

```sh
. ~/.config/machine.d/ai-gateway-env
curl -s "$AI_GATEWAY_URL/v1/chat/completions" \
  -H "Authorization: Bearer $(cat "$AI_GATEWAY_KEYS_DIR/dsh-offline")" \
  -H 'Content-Type: application/json' \
  -d '{"model":"local-fast","messages":[{"role":"user","content":"Say ok"}],"max_tokens":8}'
```

Ожидается ответ модели, а `/api/ps` показывает загруженную модель. При отказе
смотрите журнал шлюза.

**Бюджет шлюза: `402 QUOTA` «Budget exceeded: vk <агент>-online budget exceeded: X >= Y»** (AI-GW-6,
ADR-49). Это лимит шлюза на ключ (`my.ai.gateway.budget` в `modules/hosts/<хост>.nix`), а не баланс
провайдера. На `sgms-laptop` лимита нет (решение владельца 2026-11-14): расход контролируется у
провайдера, раздел бюджетов в конфиге шлюза пустой. Стоимость запросов шлюз всё равно пишет в журнал по
ценам из `my.ai.gateway.providers.<id>.prices` (у DeepSeek в политике тариф вне пика; пиковые часы
учитываются вдвое дешевле). Если после применения лимит остался в базе (старый `402`), посмотреть и
удалить его вручную (root):

```sh
sudo nix shell nixpkgs#sqlite -c sqlite3 -readonly /var/lib/private/llm-gateway-$USER/config.db \
  'select id, max_limit, current_usage, reset_duration from governance_budgets;'
sudo systemctl stop llm-gateway-$USER
sudo cp /var/lib/private/llm-gateway-$USER/config.db /var/lib/private/llm-gateway-$USER/config.db.bak
sudo nix shell nixpkgs#sqlite -c sqlite3 /var/lib/private/llm-gateway-$USER/config.db \
  "delete from governance_budgets where id = 'budget-dsh-online';"
sudo systemctl start llm-gateway-$USER
```

Откат: остановить службу и вернуть `config.db.bak`. Имена таблицы и полей — по бинарнику Bifrost 2.1.0.
Вернуть лимит — задать `my.ai.gateway.budget.maxUSD` и применить по OPS-3.

### Песочница агентов

Агент запускается только через `agent-launcher`. Если песочница сломана, он не
стартует (fail-closed, AI-A7), и обходить это нельзя. Поведение проверяет
`tests/agent-sandbox.nix` (`nix flake check`).

Корень песочницы собирается из разрешённого (R9.14, ADR-44): хранилище пакетов, `/etc`,
`/run/current-system`, сокет демона сборки — только чтение; `/dev`, `/proc`, `/tmp`, `/run` —
свои. Сокетов сессии, системной шины, `/run/secrets*` и `/run/docker.sock` внутри нет. Из
`~/.config` видны `machine.d`, `ai`, `git`, `direnv` и каталог роли (`--config`), только чтение.
У роли свои `XDG_CACHE/STATE/DATA_HOME` в `~/.local/state/agents/<роль>/`. Ключ шлюза попадает в
окружение агента значением. Состояния шлюза в `$HOME` больше нет (R9.16). `dsh` подключается нативно (R9.18, AI-ROLE-5): шлюз — `DEEPSEEK_BASE_URL`, ключ — `DEEPSEEK_API_KEY`
(значением), модель — собственные модели провайдера в интерфейсе, выбор хранит сам `dsh` в
`~/.local/state/agents/dsh/dsh-home/`; лаунчер профили не пишет. Политика Nix — патч из хранилища
флагом `--patch` (`modules/ai/_agents-tools-dsh-policy.nix`): выключены встроенный поиск, телеметрия,
выгрузка журнала сессии и перечня пакетов провайдеру (`dsh_session_log`, `dsh_plugin_packages`),
менеджер плагинов. Файл политики приоритетнее переключателей в настройках.
Если в проекте не работает `nix develop`/`direnv` — это пробел списка корня: смотрите, чего не
хватает внутри (`ls /nix/var/nix`, `ls /etc`), и правьте `_agents-tools-sandbox.nix`.

**Сеть агентов (R9.20, AI-SBX-5, AI-SEC-6, ADR-47; замена схемы R9.17 с мостами).** Песочница
работает в своём пространстве имён сети и пользователя, созданном `pasta`. Соединения агента
выходят **сокетами хоста**: по маршрутам хоста (туннель, корпоративные VPN, переключатель
маршрута) и через резолвер хоста (корпоративные зоны), любым протоколом — SSH и базы данных
работают так же, как у пользователя. Правила `nftables` загружает охранник (`agents-net guard`)
внутри пространства до старта песочницы; агент во вложенном пространстве пользователя прав над
сетью не имеет (`nft` изнутри отказывает). Не поднялась сеть или не загрузились правила — агент
не стартует (AI-SBX-6). Абстрактные сокеты хоста (графическая сессия, шины) в пространстве
недоступны. Свой `resolv.conf` песочницы указывает на пересылку DNS стека (`169.254.1.1`).

| Режим | Что доступно | Сокет демона сборки |
|---|---|---|
| `online` (по умолчанию) | сеть как у пользователя: интернет, все VPN хоста и их DNS-зоны, loopback и адреса хоста (БД и службы контейнеров на `localhost`, серверы разработки), шлюз (ключ `<агент>-online`). Закрыт порт RPC торрент-демона (D21, `my.net.sensitiveLoopbackPorts`) | виден |
| `offline` | шлюз (ключ `<агент>-offline`), DNS и сети VPN; адреса самого хоста (в том числе на линке VPN) закрыты раньше сетей VPN; интернета, LAN и остального loopback нет | скрыт |

Сети VPN — маршруты через линки корпоративных зон (`my.tunnel.dns.scopedZones.*.link`) **на момент
запуска**: VPN, поднятый позже, не виден в `offline` до перезапуска агента. Все VPN доступны всем
проектам. В M1 прокси-переменные (`http_proxy`, `https_proxy`, `no_proxy`) проходят из окружения
запуска как есть, SOCKS (`all_proxy`) не передаётся; в M2 переменных нет.

**Облако по умолчанию разрешено.** `offline` включают корни с `cloud = "deny"` в
`~/.config/ai/roots.toml` (в dotfiles: `ai/roots.toml`; запись `[[root]]`, `path = "~/…"`; корень
включает вложенные каталоги) и флаг `agent-launcher <агент> --offline` на один запуск. **Проект с
ограничениями работодателя или заказчика внесите в `roots.toml` до работы с ним** — иначе агент
увидит его как обычный (AI-SEC-9). Маркер `.ai/offline` и флаг `--online` удалены: политику задаёт
владелец, проект её не меняет (AI-SEC-5). Файл `roots.toml` есть, но не разобран или с неверным
`cloud` — запуск отказывает (а не молчаливо `online`); файла нет — все проекты `online`.
`claude` (подписка) в `offline` не запускается. Режим печатается первой строкой запуска.
Веб-интерфейс `dsh` слушает внутри песочницы порт `portBase + 100 + (uid − 1000)` и публикуется
**только на `127.0.0.1` хоста** тем же портом (`http://127.0.0.1:<порт>/…`); порт занят — агент не
запускается. Других автоматических публикаций портов агента нет.
В `offline` окружение проекта (`nix develop`/direnv) **не применяется**: демона сборки нет, и
`use flake` в direnv обращается к `nix` даже при прогретом кэше роли (проверено на машине
2026-11-07: `error: cannot connect to socket ...`). Агент запускается, но без инструментов
devshell проекта; как с этим жить — решает владелец.
Проверка — `tests/agent-network.nix` (настоящие лаунчер, песочница, `pasta` и правила; заглушки
ролей, «корпоративный VPN» с DNS-зоной в netns, «интернет» за маршрутом по умолчанию).

**Работа на месте (R9.15, AI-SBX-7, ADR-44).** Агент работает в текущем дереве проекта (корень
git-дерева), правки видны сразу, коммиты в текущую ветку разрешены. Только чтение: `.git/config`,
`config.worktree`, `hooks`, `info`, каталог `core.hooksPath` внутри дерева, `.git`-файлы и
config/hooks/info подмодулей, указатели связанных деревьев, `.envrc`. `.git` привязан к себе
(`mv .git` не проходит). Объекты, ссылки и индекс — на запись. `.direnv` у роли свой:
`~/.local/state/agents/<роль>/direnv/<хэш>`; в проекте остаётся пустой каталог `.direnv`.
Что не закрыто: `hooks/`, `info/`, `config.worktree`, которых в репозитории не было, и `.envrc`,
которого не было, агент может создать (заглушки не создаются) — первые три отчёт показывает.
Для `claude` (`--home-rw`) это ограждение, а не граница: каталог проекта и `$HOME` открыты.

После сессии лаунчер печатает отчёт `agents-git`: ссылки, сдвинутые вне текущей ветки, смена ветки,
`refs/replace`, флаги индекса (`skip-worktree`, `assume-unchanged`), новые вложенные репозитории,
появившиеся `hooks/info/config.worktree`, изменённые игнорируемые файлы (проверяются первые 20000).
Без отклонений — одна строка. Отчёт сообщает, откат делает человек. Слияние и публикация — только
человек.

Хук сканера секретов репозитория включается один раз: `just hooks` (оболочка разработки хук не
ставит). Идентичность коммитов — `machine.d/git-identity` из `my.users.<имя>.git` (SEC-10); без
неё коммит агента не пройдёт.

## 2. Смена ключей

Секреты пользователя — `secrets/users/<имя>.yaml`. Имена ключей:

| Ключ | Назначение |
|---|---|
| `ai.gateway.providerKey.<id>` | Ключ провайдера по нейтральному id из `my.ai.gateway.providers` (ADR-45); читает только root |

Ключи доступа и вход в управляющий API шлюза в sops не хранятся: их генерирует служба (раздел 1).

```sh
just sops-edit secrets/users/<имя>.yaml
just build <host> && nvd diff /run/current-system result
just test <host>    # смена секрета перезапускает llm-gateway-<имя> сама (restartUnits)
just boot <host>
```

Откат: вернуть файл секретов из git (`git revert`), снова `just test` и перезапуск юнита.
У провайдера старый ключ отзывается после проверки живым запросом (раздел 1).

## 3. Очистка журналов и состояния

Журналы локальные, содержимое запросов по умолчанию не пишется (AI-GW-7, AI-SEC-7).

| Что | Где | Перед очисткой |
|---|---|---|
| Журнал запросов шлюза | `/var/lib/private/llm-gateway-<имя>/logs.db*` (root) | Остановить юнит; пересоздание базы при старте — ПРОВЕРИТЬ |
| Журнал юнита | `journalctl -u llm-gateway-<имя>` | Общие лимиты journald |
| Сессии и кэши агентов | `~/.local/state/agents/<роль>/` | Работа агента — в самих проектах (AI-SBX-7), здесь только состояние |

```sh
sudo systemctl stop llm-gateway-$USER
sudo rm /var/lib/private/llm-gateway-$USER/logs.db*
sudo systemctl start llm-gateway-$USER
```

Отката у удаления нет. Если журнал ещё может понадобиться, перенесите его, а не удаляйте.

## 4. Модели

```sh
inference-release                                   # выгрузить всё из VRAM; без прав администратора
curl -s http://127.0.0.1:11434/api/tags             # что скачано
curl -s http://127.0.0.1:11434/api/pull -d '{"model":"<тег>"}'     # скачать заново
```

Роли и теги задаёт фича инференса по классу VRAM (AI_SUBSYSTEM P.2), а не dotfiles.
Они попадают в `my.ai.local` и `~/.config/machine.d/ai-env`. Смена тега проходит через
OPS-3; при старте сервис догружает модели сам.

Время жизни в простое — `my.ai.inference.keepAlive` (сейчас `5m`). Одновременно в VRAM
не больше одной модели (AI-RES-1).

**Фоновые сессии Claude (`claude --bg`, ←, `claude agents`; AI-SBX-13, AI-A20, ADR-48).** Все процессы
claude — в одной долгоживущей песочнице пользователя: транзиентный юнит `agents-claude.service`, его
поднимает первый `agent-launcher claude`, окна входят в неё. Фоновые сессии переживают закрытие
терминала и открываются из любого нового окна (`agent-launcher claude -- agents`, Enter); при выходе из
сеанса песочница останавливается, сессии открываются как завершённые. Состояние — штатное в `~/.claude`.

```sh
systemctl --user status agents-claude      # жива ли песочница, процессы внутри
journalctl --user -u agents-claude -n 50   # почему не поднялась (лаунчер печатает то же при отказе)
systemctl --user stop agents-claude        # остановить ВСЁ: окна и фоновые сессии
```

Новое поколение системы песочница подхватывает при следующем старте юнита (выход из сеанса или
`stop`) — активация её не перезапускает, фон не теряется. При старте песочница очищает реестр живых
процессов `~/.claude/sessions` (D23): Claude считает «живыми» записи чужого пространства PID. Если до
R9.25 остались пустые файлы `~/.claude/daemon*` и каталог `~/.local/state/agents/claude/private/` —
это точки монтирования старой подмены; удалить без запущенного claude:
`find ~/.claude -maxdepth 1 -name 'daemon*' -empty -delete`. Проект вне `$HOME` долгоживущей песочнице
недоступен — лаунчер откажет с объяснением. Веб-интерфейс `dsh` с хоста: `http://127.0.0.1:11600/`
отвечает 401 без токена и 303 с токеном; после остановки порт закрыт, мостов и каталога

окружение проекта собирается через демон (после `NIX_REMOTE=daemon`), в `offline` — нет (см. выше).

### Исправление AI-INF-8 (2026-11-05)

1. `my.ai.inference.modelsDir` по умолчанию — `/var/lib/nosnapshot/models`, подкаталог тома данных (`@data`), который `backup` не снимает.
2. У сервиса Ollama статическая учётная запись `ollama`: при `DynamicUser` владелец каталога на другом томе заранее неизвестен. Песочница сервиса сохраняется (`ProtectSystem=strict`, запись только в каталог моделей). Каталог создаёт `systemd-tmpfiles` с правами `0750`.
3. `backup` читает `modelsDir` и не даёт собрать систему, если каталог лежит на подтоме из снимков (`rootfs`, `home`). Путь при этом не дублируется. Список моделей в снимки не попадает и составом: подтом `data` в btrbk не перечислен.
4. Тест `tests/inference-models-dir.nix`: права, владелец и запись из песочницы сервиса.

### Тест `finegrained` (AI-A3)

NVIDIA заявляет RTD3 в открытых модулях только с Ampere ([README 595](https://download.nvidia.com/XFree86/Linux-x86_64/595.58.03/README/kernel_open.html)),
а у `sgms-laptop` Turing. Поэтому тест в два этапа. Этап А на открытых модулях (2026-11-05,
драйвер 595.71.05) дал `Runtime D3 status: Not supported`, `runtime_status = active`. Проприетарные модули
Turing поддерживают.

Условия замера: батарея, внешний монитор отключён (hosts/sgms-laptop.md), 10 минут простоя.
`nvidia-smi` не запускать: он будит GPU.

```sh
P=/sys/bus/pci/devices/0000:01:00.0/power
cat $P/control $P/runtime_status $P/runtime_suspended_time
cat /proc/driver/nvidia/gpus/0000:01:00.0/power
upower -i "$(upower -e | grep BAT)" | grep energy-rate
```

| Этап | Что меняется | `runtime_status` | `Runtime D3 status` | Мощность простоя |
|---|---|---|---|---|
| База | `finegrained = false` | active | Disabled by default | Снять |
| А | `finegrained = true` | Снять | Снять | Снять |
| А (2026-11-05) | `open = true`, `finegrained = true` | active, `control = auto` | **Not supported** | Не снимали |
| Б (2026-11-05) | `open = false`, `finegrained = true`; `license: NVIDIA`, `DynamicPowerManagement: 2` | active, `control = auto` | **Not supported** | 18,0 Вт |
| Б2 (2026-11-05) | то же и `NVreg_EnableGpuFirmware=0` | **suspended**, `control = auto`, `runtime_suspended_time` 746 289 мс | **Enabled (fine-grained)** | 15,5 Вт (единичный замер; база 18,0 Вт) |

Причина `Not supported` — GSP-прошивка: с ней RTD3 на Turing не включается ни на открытых, ни на
проприетарных модулях. Принят вариант Б2. Остаётся AI-A5 (три цикла гибернации с инференсом на GPU),
AI-A4 (игра) и проверка CUDA без GSP (A7).

Перед Б2 проверено (read-only): chassis_type 10, у корневого порта `PEG0` есть `power_resources_D0` и `power_resources_D3hot` (`_PR0/_PR3`), чипсет HM470, Turing, ядро 6.18.60, CONFIG_PM, persistenced выключен. Условия README 595 выполнены, а драйвер всё равно пишет `Not supported`.

Этап А и Б применяются через `just boot` и перезагрузку: параметры модуля читаются при его
загрузке. Этап Б меняет запись в A.6 Архитектуры и требует заново проверить A7 (CUDA).

Критерий приёмки варианта:

1. После `inference-release` статус `suspended`, мощность простоя ниже базы (AI-A3).
2. Три цикла hibernate подряд, инференс на GPU после каждого (AI-A5).
3. Игра идёт на dGPU, FIM после неё загружается по требованию (AI-A4).

Если устройство всё равно держит процесс, посмотреть `sudo lsof /dev/nvidia*`. Если это демон
инференса, это отдельная находка для фичи инференса.

Откат на любом этапе — предыдущее поколение. Если ни один вариант не прошёл, вернуть
`finegrained = false` и записать исключение AI-A3/A5 здесь; решение по G8 принимает владелец.

# Runbook — замена ключей

Ключи sops (пользователь, хост), `.sops.yaml`, ротация при компрометации. Правила — SEC-7,
SEC-8, SEC-11, SEC-12, SEC-13 (`grep -n "SEC-" docs/architecture/ARCHITECTURE.md`).

> Значения ключей и секретов здесь не пишутся (SEC-5): только пути, команды и плейсхолдеры `<…>`.
> Команды выполняет человек; ассистент секреты не читает и ключи не создаёт.

Ротация конкретных секретов — в тематических runbook:

- клиенты и адрес выхода туннеля — [`tunnel.md`](tunnel.md), процедуры 3 и 4;
- ключ провайдера агентов (`my.ai.agentKeys`) — [`ai.md`](ai.md), раздел про смену ключей.

## 1. Что есть

| Ключ | Где живёт | Что открывает |
|---|---|---|
| age-ключ пользователя | `~/.config/sops/age` (подтом `home`, входит в снимки и копию — SEC-13) | файлы `secrets/*.yaml`, у которых он в получателях |
| age-ключ хоста | выводится из SSH host-ключа ed25519 (`/etc/ssh` на подтоме `rootfs`, входит в копию); путь задаёт `services.openssh.hostKeys`, его читает `sops.age.sshKeyPaths` (`modules/security/sops.nix`) | расшифровку секретов при активации системы |

Получатели — только публичные ключи — перечислены в `.sops.yaml` (SEC-7). Сейчас три правила:
`secrets/common.yaml`, `secrets/hosts/sgms-laptop.yaml`, `secrets/users/sgm.yaml`, у каждого — два
получателя (ключ пользователя и ключ хоста; у пользователя один хост, отдельного получателя-хоста для
него нет). Какой секрет в каком файле и кто его читает — `secrets/README.md`.

Потеря единственного ключа = потеря секретов (SEC-13): отдельную офлайн-копию ключей хранить вне диска.

## 2. Добавить или заменить ключ (плановая замена)

Исходное условие: есть хотя бы один рабочий ключ из получателей (иначе `updatekeys` нечем расшифровать).

```sh
# 1. Новый ключ пользователя (если заменяется он)
age-keygen -o ~/.config/sops/age/keys.txt   # публичный ключ выведется в stdout; приватный не печатать

# 2. Публичный ключ хоста из SSH host-ключа (если заменяется он)
ssh-keygen -y -f /etc/ssh/ssh_host_ed25519_key | ssh-to-age   # ПРОВЕРИТЬ: пакеты age, ssh-to-age в devshell

# 3. Внести новый публичный ключ в .sops.yaml (старый — убрать только после шага 4)
$EDITOR .sops.yaml

# 4. Перешифровать файлы под новый список получателей
just sops-rekey          # sops updatekeys secrets/*.yaml

# 5. Проверить и применить по OPS-3
just check
just build sgms-laptop && just test sgms-laptop
```

Затем убрать из `.sops.yaml` старый публичный ключ и снова `just sops-rekey`. Одного `updatekeys`
достаточно только для плановой замены: прежний ключ продолжает открывать **старые** версии файлов в
истории git. Если старый ключ скомпрометирован — раздел 3.

Путь к ключу пользователя sops по умолчанию ищет в `~/.config/sops/age/keys.txt` (стандарт sops);
если путь иной — переменная `SOPS_AGE_KEY_FILE`. ПРОВЕРИТЬ на машине, где лежит файл ключа.

## 3. Ключ скомпрометирован или утёк (SEC-11)

Секрет, который был доступен постороннему (в публичной истории, в чате, на чужом диске), считается
скомпрометированным: смена ключа получателя его **не** защищает.

1. Сгенерировать новый ключ и заменить получателя по разделу 2.
2. **Заменить значения** всех секретов, к которым открывал доступ старый ключ (перечень — таблица в
   `secrets/README.md`): выпустить новые на стороне источника (выход туннеля, провайдер моделей, VPN),
   записать через `just sops-edit <файл>`.
3. Отозвать старые значения на стороне источника — это и есть замена; без неё старый ключ остаётся рабочим.
4. Прогнать `bash scripts/check-secrets.sh` и `just check`; применить по OPS-3.
5. Если утечка в публичную историю git — история не переписывается (`.mailmap`, ADR-47); защищает только
   замена значений.

## 4. Новый хост и новый пользователь

`just add-host` и `just add-user` — **заготовки, не реализованы** (`justfile`). Ручной порядок —
ARCHITECTURE.md §18.3 (пункт 4) и §18.4 (пункт 3): создать ключ, добавить получателя в `.sops.yaml`
(новое правило `path_regex` для файла хоста или пользователя), `just sops-rekey`. Ключ хоста должен
оказаться на машине **до** первой активации (SEC-12) — см. [`recovery.md`](recovery.md).
